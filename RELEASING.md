# Выпуски Xkeen-UI: ветки, теги, беты

Правила для всех, кто ставит теги. Тег запускает сборку выпуска: из тега берутся номер версии, канал (стабильный или тестовый) и подписанный каталог модулей. Неправильный тег — это неправильный выпуск у пользователей.

## Ветки

| Ветка | Назначение |
|---|---|
| `pre-release` | Вся работа и беты. Коммиты идут сюда. |
| `main` | Только стабильные выпуски. Напрямую в `main` не коммитим. |

`pre-release` — общая ветка: rebase не делаем, чужие коммиты вливаем через `git merge`.

## Перед коммитом: описи

Опись модулей строится по `git ls-files`, а размеры модулей сами входят в опись. Если пересобрать её до `git add` новых файлов или не в том порядке, локально всё зелёное, а CI после пуша красный. Поэтому:

1. Один раз: `git config core.hooksPath .githooks`. Хук `pre-commit` проверяет коммит по его точному содержимому и не пропускает устаревшую опись.
2. Новые файлы — сначала `git add`, потом `npm run inventory:refresh`. Команда сама прогоняет все генераторы в нужном порядке, пока результат не перестанет меняться, и отказывается работать, если в `xkeen-ui/`, `tests/`, `e2e/`, `scripts/`, `docs/` лежат файлы, не добавленные в git.
3. Добавить обновлённые описи в коммит (команда перечислит их).

Проверить вручную без коммита: `npm run inventory:check`.

## Перед тегом: весь e2e

Браузерных тестов нет в CI, поэтому зелёный CI их не показывает. Хук `pre-push` не пропустит тег `v*` или `module-*`,
если на его коммите не прошёл весь e2e.

1. Перейти на коммит будущего тега. Незакоммиченных правок быть не должно.
2. `npm run e2e:gate`: сборка фронта и весь e2e, упавшие тесты повторяются один раз. При успехе коммит отмечается локально.
3. Поставить и запушить тег как обычно.

Пропустить разово, например для срочной правки: `XKEEN_SKIP_E2E_GATE=1 git push origin <тег>`.

## Перед тегом панели: версии модулей

Модули выпускаются и отдельно от панели, поэтому у каждого своя версия в `module-versions.json`. На теге `v*`
сборка выпуска запускает `scripts/check_module_versions_for_release.py`, и тот же хук `pre-push` проверяет это
до пуша — иначе тег уже выдан, а номер беты потерян. Два правила:

1. **Правка модуля — подъём его версии.** Если с ближайшего тега панели-предка (любого канала) менялись файлы
   модуля — Xray, Mihomo, редакторы, файлы, терминал, резервные копии, утилита ссылок подписок, диагностика, —
   его версия должна быть выше, чем в том теге (`1.0.0` → `1.0.1`). Какие файлы чьи — `module-ownership.json`
   сборки. Достаточно поднять один раз за выпуск панели, не на каждый коммит.
2. **Выпущенный модуль — влить его ветку.** Версия не может быть ниже уже выданного тега `module-<id>-*`: после
   выпуска модуля его ветку вливают в `pre-release` (`git merge`), иначе следующая панель откатила бы модуль.

Хук смотрит версии в самом теге, а не в рабочей папке. Теги модулей коллег — после `git fetch --tags`.
Пропустить разово: `XKEEN_SKIP_MODULE_VERSIONS=1 git push origin <тег>` (сборка выпуска всё равно проверит).

## Формат тегов

| Выпуск | Тег | Версия в панели и `BUILD.json` |
|---|---|---|
| Стабильный | `vX.Y.Z` | `X.Y.Z` |
| Бета | `vX.Y.Z-beta.N` | `X.Y.Z-beta.N` |

- Приставка `v` — часть тега, в номер версии она не входит.
- Никаких букв в конце (`v2.9.2a`) и точки после `v` (`v.2.8.8`). Каталог модулей сравнивает версии по semver, и такой тег сломает обновление.
- Тег с дефисом (`-beta.N`) сборка публикует как пререлиз, тег без дефиса — как стабильный выпуск (latest).

## Порядок бет — строго по очереди

После стабильного `vX.Y.Z` беты к следующему выпуску идут как `vX.Y.(Z+1)-beta.N`, номера с 1, **без пропусков и повторов**:

```
v3.0.2            стабильный
v3.0.3-beta.1     первая бета к 3.0.3
v3.0.3-beta.2
v3.0.3-beta.3
v3.0.3            стабильный
v3.0.4-beta.1     …
```

Если в выпуске крупная новая функция и решено поднять второй номер, беты начинаются заново: `v3.1.0-beta.1`. Решение принимается до первой беты этой линии.

Беты ставят разные люди, поэтому перед тегом:

1. `git fetch --tags` и `git tag -l "vX.Y.*" | sort -V | tail` — посмотреть последние теги.
2. Проверить выпуски на GitHub (Releases): тег мог появиться, пока вы работали.
3. Взять **следующий свободный** номер.

## Проверка тега в сборке

Первый шаг обеих сборок по тегу — `scripts/check_release_tag.py`. Если тег нарушает правила выше, сборка падает до публикации выпуска, и в журнале написано, что не так и какой тег правильный. Проверка не пускает:

- тег не формата `vX.Y.Z` / `vX.Y.Z-beta.N`;
- версию не выше последнего стабильного выпуска или с пропуском номеров (после `3.0.2` допустимы `3.0.3`, `3.1.0`, `4.0.0`);
- бету ниже уже открытой линии бет;
- `beta.N` не сразу за `beta.N-1`, и не `beta.1` для версии, у которой бет ещё нет;
- стабильный тег на коммите, которого нет в `main`.

Тег, отклонённый проверкой, удалите (`git push origin :refs/tags/<тег>` и `git tag -d <тег>`) и поставьте правильный.

Какой тег ставить следующим, подскажет сама проверка:

```sh
git fetch --tags
python scripts/check_release_tag.py --next
```

## Как поставить бету

1. Коммиты запушены в `pre-release`, CI на этом коммите зелёный.
2. Аннотированный тег на этот коммит:
   ```sh
   git tag -a v3.0.3-beta.1 -m "Xkeen-UI v3.0.3-beta.1" <коммит>
   git push origin v3.0.3-beta.1
   ```
3. Дождаться сборки по тегу и проверить выпуск: помечен как пререлиз, архив и `.sha256` на месте, `catalog.json` с `.sig`, версия в `BUILD.json` совпадает с тегом.

## Как выпустить стабильную версию

1. `pre-release` запушен, CI зелёный.
2. `main` **перематывается** до `pre-release`, без force и без коммитов в `main`:
   ```sh
   git merge-base --is-ancestor origin/main pre-release   # main должен быть предком
   git push origin pre-release:refs/heads/main
   ```
   Если `main` не предок `pre-release` — стоп, сначала разобраться.
3. CI на `main` зелёный.
4. Аннотированный тег `vX.Y.Z` на тот же коммит, `git push origin vX.Y.Z`.
5. Проверить выпуск: не пререлиз, latest, `catalog.json.sig`, sha архива, версия в `BUILD.json`.

## Срочная правка стабильной версии

Когда в `pre-release` уже есть неготовое к выпуску:

1. Ветка от `main` → правка и тесты.
2. Тег `vX.Y.(Z+1)` на этой ветке.
3. `main` перемотать на неё.
4. Сразу `git merge` этой ветки в `pre-release` и запушить.

## Выпуск одного модуля

Правка только в файлах модуля может выйти без выпуска панели. Файлы ложатся в GitHub Release панели `V`, от которой
сделана правка: архив `xkeen-module-<id>-X.Y.Z.tar.gz` с `.sha256` и подписанный `module-updates.json`. Отдельного
выпуска у модуля нет, бет модулей нет, отзыва нет: плохой выпуск исправляется следующим, с версией выше.

1. Ветка `module/<id>-<версия>` **от тега панели `V`**, а не от `pre-release`: в `pre-release` core уже другой.
   `V` — последний опубликованный выпуск своего канала (стабильный или бета). Правка для беты делается от тега беты
   и видна только на ней. Если от этой же `V` модуль уже выпускался, ветка режется **от последнего тега
   `module-<id>-*` этой панели**, а не от `V`: иначе новый выпуск заменит прежний на роутерах без его правки.
   `check_module_release.py` это проверяет: каждый выданный тег модуля от той же `V` должен быть предком выпуска,
   иначе «ОШИБКА» с именем недостающего тега.
   ```sh
   git fetch --tags
   git tag -l "module-tool.files-*" --contains v3.1.0   # уже выданные выпуски модуля от v3.1.0 и позже
   git switch -c module/tool.files-1.0.1 v3.1.0                    # первый выпуск модуля от v3.1.0
   git switch -c module/tool.files-1.0.2 module-tool.files-1.0.1   # следующий от той же v3.1.0
   ```
2. Правка только файлов модуля (вне `xkeen-ui/` можно менять `module-versions.json`, `tests/`, `e2e/`, `docs/`).
   `xkeen-ui/module-sizes.json` пересчитывается хуком вместе с описями — его проверка сравнивает по смыслу:
   меняться может только запись выпускаемого модуля (размеры считаются по файлам пакета, без тестов и e2e).
   Файлы, которые кладёт только сборка выпуска панели (`retired-files.json`, `BUILD.json`), не сравниваются —
   ни сами, ни их строки в `module-ownership.json`.
   Поднять версию модуля в `module-versions.json`, тесты, `npm run e2e:gate` на коммите тега.
3. Тег `module-<id>-X.Y.Z` на этом коммите (версия — как в `module-versions.json`, выше уже выданных тегов модуля):
   ```sh
   git tag -a module-tool.files-1.0.1 -m "Модуль tool.files 1.0.1" <коммит>
   git push origin module-tool.files-1.0.1
   ```
   Хук `pre-push` требует отметку e2e и для тегов `module-*`. Тег не начинается с `v`, поэтому сборку панели и
   `check_release_tag.py` он не запускает.
4. Workflow `release-module.yml`: тесты, затем `scripts/check_module_release.py` против архива панели `V` и списка
   опубликованных выпусков. Если правка выходит за файлы модуля, workflow останавливается с сообщением
   «Нужен выпуск панели» — это штатный исход: правка уходит в выпуск панели. Иначе прежний `module-updates.json`
   скачивается и проверяется подписью (его нет — это первый выпуск, `serial` 1), собирается следующий документ
   (`serial` + 1, заменяется только запись этого модуля), подписывается ключом `release-2026` и выгружается
   `gh release upload "$V" --clobber` в порядке: архив и `.sha256`, затем `module-updates.json`, затем `.sig`.
   Публикации идут по одной (`concurrency: module-release`).
   **Теги модулей пушить по одному и ждать конца прогона.** Группа `concurrency` держит только один ждущий прогон:
   если в очередь встанет третий, GitHub отменит ждущий, и его тег останется выданным, но не опубликованным.
   Отменённый прогон перезапустить (Re-run all jobs), когда закончится текущий.
5. Проверить выпуск панели `V`: на месте архив модуля, `.sha256`, `module-updates.json` и `.sig`.
6. Влить ветку в `pre-release` через `git merge` (не rebase) и запушить. Без этого следующая панель выйдет со старой
   версией модуля: проверка при выпуске панели требует, чтобы версия в `module-versions.json` была не ниже выданных
   тегов `module-<id>-*`.

Если выгрузка оборвалась между документом и подписью (на выпуске новый `module-updates.json` со старым `.sig`),
роутеры отвечают прежней копией, а следующий прогон останавливается на проверке подписи прежнего документа.
Починка: скачать `module-updates.json.sig` из артефакта `module-release` этого прогона (вкладка Actions, Artifacts;
артефакт выгружается шагом раньше публикации, поэтому он есть у каждого прогона, дошедшего до неё) и выгрузить
`gh release upload "$V" module-updates.json.sig --clobber`. Перезапускать прогон до этого бесполезно.
Удалить сломанный `module-updates.json` и перезапустить прогон можно только если это был первый документ этой
панели (`serial` 1): иначе прогон соберёт документ заново с `serial` 1 без записей прежних выпусков, и роутеры
его отвергнут как откат. По той же причине документ с выпуска руками не удалять: роутер, у которого уже есть его
копия, на 404 отвечает копией и до перехода на следующую панель показывает «Обновления модулей сейчас не проверить».

Схема держится на том, что выпуски изменяемые: если включить неизменяемые выпуски в настройках репозитория,
ассеты модулей к выпуску панели больше не добавить.

## Что ещё запускает тег

На тег `v*` срабатывают две сборки: пользовательский архив с выпуском (`build-user-archive.yml`) и бета Android-приложения (`publish-android-beta.yml`). Тег `module-*` запускает только `release-module.yml`.
