# Выпуски Xkeen-UI: ветки, теги, беты

Правила для всех, кто ставит теги. Тег запускает сборку выпуска: из тега берутся номер версии, канал (стабильный или тестовый) и подписанный каталог модулей. Неправильный тег — это неправильный выпуск у пользователей.

## Ветки

| Ветка | Назначение |
|---|---|
| `pre-release` | Вся работа и беты. Коммиты идут сюда. |
| `main` | Только стабильные выпуски. Напрямую в `main` не коммитим. |

`pre-release` — общая ветка: rebase не делаем, чужие коммиты вливаем через `git merge`.

## Формат тегов

| Выпуск | Тег | Версия в панели и `BUILD.json` |
|---|---|---|
| Стабильный | `vX.Y.Z` | `X.Y.Z` |
| Бета | `vX.Y.Z-beta.N` | `X.Y.Z-beta.N` |

- Приставка `v` — часть тега, в номер версии она не входит.
- Никаких букв в конце (`v2.9.2a`) и точки после `v` (`v.2.8.8`). Каталог модулей сравнивает версии по semver, и такой тег сломает обновление.
- Тег с дефисом (`-beta.N`) сборка публикует как пререлиз, тег без дефиса — как стабильный выпуск (latest).

## Порядок бет — строго по очереди

После стабильного `vX.Y.Z` беты к следующему выпуску идут как `vX.Y.(Z+1)-beta.N`, номера с 1, **без пропусков и повторов**:

```
v3.0.2            стабильный
v3.0.3-beta.1     первая бета к 3.0.3
v3.0.3-beta.2
v3.0.3-beta.3
v3.0.3            стабильный
v3.0.4-beta.1     …
```

Если в выпуске крупная новая функция и решено поднять второй номер, беты начинаются заново: `v3.1.0-beta.1`. Решение принимается до первой беты этой линии.

Беты ставят разные люди, поэтому перед тегом:

1. `git fetch --tags` и `git tag -l "vX.Y.*" | sort -V | tail` — посмотреть последние теги.
2. Проверить выпуски на GitHub (Releases): тег мог появиться, пока вы работали.
3. Взять **следующий свободный** номер.

## Как поставить бету

1. Коммиты запушены в `pre-release`, CI на этом коммите зелёный.
2. Аннотированный тег на этот коммит:
   ```sh
   git tag -a v3.0.3-beta.1 -m "Xkeen-UI v3.0.3-beta.1" <коммит>
   git push origin v3.0.3-beta.1
   ```
3. Дождаться сборки по тегу и проверить выпуск: помечен как пререлиз, архив и `.sha256` на месте, `catalog.json` с `.sig`, версия в `BUILD.json` совпадает с тегом.

## Как выпустить стабильную версию

1. `pre-release` запушен, CI зелёный.
2. `main` **перематывается** до `pre-release`, без force и без коммитов в `main`:
   ```sh
   git merge-base --is-ancestor origin/main pre-release   # main должен быть предком
   git push origin pre-release:refs/heads/main
   ```
   Если `main` не предок `pre-release` — стоп, сначала разобраться.
3. CI на `main` зелёный.
4. Аннотированный тег `vX.Y.Z` на тот же коммит, `git push origin vX.Y.Z`.
5. Проверить выпуск: не пререлиз, latest, `catalog.json.sig`, sha архива, версия в `BUILD.json`.

## Срочная правка стабильной версии

Когда в `pre-release` уже есть неготовое к выпуску:

1. Ветка от `main` → правка и тесты.
2. Тег `vX.Y.(Z+1)` на этой ветке.
3. `main` перемотать на неё.
4. Сразу `git merge` этой ветки в `pre-release` и запушить.

## Что ещё запускает тег

На тег `v*` срабатывают две сборки: пользовательский архив с выпуском (`build-user-archive.yml`) и бета Android-приложения (`publish-android-beta.yml`).
