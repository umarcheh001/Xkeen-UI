# Этап 8.6: UI менеджера модулей

**Статус:** реализация готова; ожидает итоговой проверки подэтапа 8.6.

`/modules` — core-owned экран обслуживания панели. Его template,
`modules-manager.css`, page entry и `features/module_manager/` входят в core;
контроллер не импортирует DevTools. Стабильная ссылка из DevTools ведёт сюда,
а расширенная диагностика остаётся необязательной.

Карточка «Обновление панели» в DevTools справочная для любого канала: версия,
сборка, источник, профиль и состав модулей. Кнопок проверки, обновления и
отката в ней нет. Сборка с канала `main` (локальная, без подписанного
release-пакета) из интерфейса не обновляется: её обновляют установщиком
`install.sh`. Серверный путь `main` (`/api/devtools/update/*` с
`development_only: true`) сохранён для прежних вызовов.

## Загрузка и навигация

При входе экран запрашивает установленные модули и текущий статус операции.
Вкладка «Установленные» показывает версию панели, профиль, переключатели и
разрешённые сервером действия. Вкладка «Доступные» загружает каталог только
при первом открытии. Ошибка каталога не мешает просмотру установленного
состояния; ручной повтор выполняется повторным открытием вкладки/обновлением
страницы. Статус должен быть успешно получен до любой мутации. При ошибке
статуса действия блокируются, а кнопка обновления статуса позволяет повторить
запрос. Работающий процесс опрашивается до терминального результата.

## План и применение

Кнопки установки, восстановления, удаления, обновления/отката панели и
перехода профиля сначала запрашивают read-only server plan. Диалог показывает
область операции, затронутые модули, версии, число добавляемых/удаляемых
файлов, нужное место, diff зависимостей, требование restart и blockers.
`Apply` доступен только для применимого плана с `plan_id`; закрытие диалога
ничего не устанавливает. Сервер повторно проверяет план при apply. Код
`module_plan_stale` или `operation_plan_stale` закрывает прежний план: нужно
запросить и проверить новый. Переключатель «Включён» меняет состояние модуля,
но не устанавливает и не удаляет его файлы.

## Отмена, восстановление и restart

Для `running` экран показывает ход операции и журнал шагов. «Отменить
операцию» отправляет запрос runner; окончательный результат определяет runner
и может включать rollback. После терминального статуса экран обновляет
установленное состояние. Для `interrupted` доступно «Восстановить операцию»;
восстановление не перезапускает панель автоматически. При `rollback_failed`
новые действия блокируются: нужна ручная проверка файлов и журнала по
[`Lifecycle API runbook`](modular-panel-stage8-lifecycle-api.md#ручное-восстановление).

«Перезапустить панель» появляется только после свежего терминального статуса
`committed` или `rolled_back` с `restart_required`, когда физический переход
профиля не ожидается. Повторный запрос после принятого restart блокируется.
Это перезапуск службы панели, а не отдельного proxy core.

## Offline, trust и rollback

Каталог и архивы поступают только из официального release и проверяются
сервером. UI не принимает произвольные URL, ключи или неподписанные пакеты;
ошибки доверия и устаревшего/недоступного каталога показываются как ошибки с
кодом. Offline не скрывает уже установленное состояние и не запускает
скачивание: пакет загружается лишь после явного подтверждения применимого
плана. При ошибке установки rollback выполняет transaction runner; UI
показывает его результат, но не обещает восстановление при
`rollback_failed`. Panel rollback является отдельной операцией с просмотром
плана и появляется только при доступной предыдущей версии.

API и пределы транзакции описаны в
[`modular-panel-stage8-lifecycle-api.md`](modular-panel-stage8-lifecycle-api.md)
и [`modular-panel-stage8-panel-profile.md`](modular-panel-stage8-panel-profile.md).
