# Mihomo node import — Этап 6: полный candidate, summary и сохранение/применение

**Статус:** закрыт 26 октября 2026 года.

Этап завершает работу из модала без имитации кликов главного toolbar. Один и тот
же подготовленный candidate используется для черновика, save-only и apply.

## Реализовано

- Добавлен единый `buildImportCandidate`: provider/static patch, `proxies`,
  `proxy-providers`, `use`/`groups`, unknown-group diagnostics и текущий
  editor snapshot собираются до действия.
- В модале доступны три действия:
  - **В черновик** — записывает candidate только в главный редактор, отмечает
    его dirty и не пишет файл, не делает backup и не запускает restart;
  - **Сохранить** — вызывает общий `/api/mihomo/import/commit` с явным
    `restart: false`, выполняет YAML + `mihomo -t`, создаёт backup и сохраняет;
  - **Сохранить и применить** — тот же pipeline, затем ставит существующий
    restart job и ждёт фактический результат `/api/restart-job/<id>`.
- Сохраняется `base_revision` активного `config.yaml`. При внешнем изменении
  backend отвечает `409 stale_config`, не валидирует и не перезаписывает файл.
- Save/apply status различает проверку, сохранение, queue/job, успех и partial
  outcome «файл сохранён, применение не удалось». Закрытие модала не отменяет
  server-side job; повторный импорт не требуется.
- Main editor помечается clean только когда его текст не изменился во время
  операции; новые параллельные правки не стираются и остаются dirty.
- Регистрация поддержанных автообновлений отделена от draft: она выполняется
  после успешного save candidate. Ошибка регистрации показывается отдельным
  warning, без повторной вставки и повторного импорта.
- Backend commit перед записью делает syntax validation и внешний `mihomo -t`,
  создаёт backup через существующий runtime helper, а apply использует текущий
  `command_job` restart pipeline.

## Проверки

- Route tests: validation, backup/apply job и stale file revision.
- Playwright: draft/save/apply controls, explicit `restart: false/true`, status
  summary и restart job completion.
- Full Mihomo import lifecycle/layout, unit/contracts, frontend build, static
  verification и inventories выполнены.

## Граница этапа

Автоматический rollback не заявляется: при partial apply показывается состояние
и существующий backup остаётся доступен штатному backup restore. Сценарии
восстановления дополнены 28 октября, как описано ниже.

## Дополнение от 28 октября 2026 года

Владелец выбрал вариант А: отдельное состояние проверки в том же модале.
Перед тремя финальными действиями показаны сводка, предупреждение о старых
несохранённых правках и раскрываемые сравнения импорта/всего файла и итоговый YAML.

- Candidate привязан к snapshot редактора, профилю и настройкам. Изменение
  после review требует новой проверки и повторного подтверждения.
- Главный редактор и модал используют общий adapter блокировки операций.
  Clean state относится к сохранённому тексту; новые правки не перетираются.
- Черновик переносит registration intents в память страницы; регистрация
  происходит после сохранения содержащего узлы конфига. Повтор регистрации
  читает свежий сохранённый файл, чтобы не активировать удалённые узлы.
- Повтор после потерянного ответа использует operation id; сервер не пишет
  и не ставит restart job повторно. Отдельный apply retry не сохраняет файл.
- Для job проверяются terminal status, exit code и error, затем процесс
  Mihomo и отдельно API. Неизвестный результат блокирует новые записи до
  восстановления наблюдения; закрытие модала не уничтожает job identity.
- Сервер повторно проверяет ревизию после `mihomo -t`. Для первого конфига
  есть baseline отсутствующего файла без создания файла при чтении.
- В batch patch исправлен случай `proxies: # комментарий`, который мог
  создать вторую секцию и потерять старые узлы при YAML-разборе.

Контрольные сценарии: unit-тесты shared adapter, route tests и
`e2e/mihomo_import_review.spec.mjs`, дополнительно lifecycle/layout E2E.
Результаты полного прогона записываются в журнал работы; проверки на
физическом роутере и автоматический rollback не заявляются.

Ограничения: job/recovery state живёт до перезагрузки страницы; серверный
idempotency cache ограничен 64 операциями и сроком жизни процесса панели.
Последняя сверка ревизии защищает от обнаруженных внешних изменений, но
произвольный внешний writer не участвует в блокировке приложения.
