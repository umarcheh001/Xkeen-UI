# Независимый выпуск и обновление модулей

Статус: одобрено владельцем 01.11.2026, проверка исполнителем пройдена, проба шага 0 выполнена. План работ и уточнения после сверки с кодом: `docs/superpowers/plans/2026-11-02-independent-module-releases.md`. База: `1f9b4ea4` (`pre-release`).

## Зачем

После выпуска панели в модуле находят ошибку или решают его переделать. Сейчас единственный способ
доставить правку — выпустить всю панель. Цель: поработать только с модулем и выпустить только его.
Ради этого затевался переход на модульную архитектуру (решение владельца, 31.10.2026).

Сценарий: панель `V` вышла → правка окна диагностики → выпущен только модуль → пользователь нажимает
«Обновить» у этого модуля → панель и остальные модули не меняются.

## Цели, не цели, чего избежать

Цели этапа 1:

- у каждого модуля своя версия вместо заглушки `REGISTRY_VERSION = "1.0.0"`;
- модуль выпускается без сборки панели, через отдельный подписанный каталог;
- обновление одного модуля — транзакция с журналом и откатом, как у `install` и `repair`;
- панель показывает доступное обновление модуля и обновляет его по кнопке;
- разделение проходит постепенно: первым отделяется `tool.advanced-diagnostics`.

Не цели этапа 1:

- совсем новые модули без выпуска панели (этап 2, см. в конце);
- работа одного выпуска модуля на нескольких версиях панели;
- полный разбор core разом;
- автообновление модулей без действия пользователя;
- ручной выбор старой версии модуля;
- модули сторонних авторов, пользовательские адреса каталога.

Чего избежать (провал, даже если формально работает):

- модуль обновился, а панель перестала открываться или смешала файлы разных сборок;
- обновление панели молча откатило выпущенную правку модуля;
- выпуск модуля требует ручной сверки, которую легко забыть;
- прикладной код незаметно продолжает оседать в core.

## Ограничения

- Роутеры: мало памяти и места, запись на flash ограничена. Python-модули и файлы фронта живут в общем
  дереве `/opt/etc/xkeen-ui`.
- Модуль без core не запускается: Python импортирует внутренности core напрямую, стабильного API нет.
- Цепочка доверия остаётся: Ed25519, ключ `release-2026`, закрытый ключ только в CI, URL строит клиент,
  ветки и пользовательские адреса запрещены.
- Панели старее разреза не читают новый каталог и должны обновляться на панель с разрезом обычным
  `panel-update` своим старым кодом.
- `git`: работа в `pre-release`, rebase запрещён, стабильный выпуск — перемотка `main` и тег `vX.Y.Z`.
- `check_release_tag.py` следит за строгим порядком тегов `v*`, `pre-push` требует отметку e2e.
- Локальные сборки (`<тег>+local.<sha>`) не выполняют операций над модулями, только смотрят.

## Подходы

Как оборвать цепочку хэшей на границе core и модуля:

1. **Постоянные имена через importmap (выбран владельцем).** Core зовёт модуль по имени
   `xk-module/<id>`, панель при выдаче страницы подставляет хэшированный файл из манифеста модуля. Имена с
   хэшем остаются, смеси старого и нового JS из кэша нет. Механизм уже есть у CodeMirror. Пригодится на этапе 2.
2. **Файлы без хэша на границах.** Меньше работы, но возвращается проблема кэша (`max-age=600`), манифест
   всё равно делить, этапу 2 не помогает.
3. **Обновление модуля заодно меняет файлы core.** Два отдельно обновлённых модуля правили бы один файл core,
   откат ненадёжен. Отброшен.

Откуда панель узнаёт о выпусках (выбрано владельцем): отдельный подписанный каталог модулей, а не модули в
выпусках панели с собственными версиями. Второй вариант не даёт выпустить модуль без выпуска панели.

Совместимость: выбрана привязка к одному выпуску панели. Стабильный договор core с модулями и диапазоны
совместимости отложены, это большая работа, а сценарию владельца она не нужна.

## Решённое устройство

### Правило совместимости

Обновление модуля собирается от тега конкретной панели `V` и подходит только ей. Минимальная версия и
максимальная совпадают: это `V`. Каталог обновлений лежит у каждой панели свой, поэтому диапазоны
вычислять не нужно. Поле `min_core` в записи равно `V`.

Правка выпускается только для последней панели своего канала, стабильные и беты считаются отдельно (решение
владельца, 01.11.2026). Модули на старые панели не ставятся: проект развивается вперёд. Если в канале уже есть панель
новее `V`, CI отказывает, и правка идёт в неё или в следующий выпуск панели. Одна правка — один выпуск, параллельных
сборок под разные панели нет. Так обновление панели не откатывает выпущенную правку.

Каждый выпуск панели несёт все модули. При обновлении панели модули обновляются вместе с ней, поэтому
модуль не окажется на сборке core новее той, под которую собран. Пользователь старой панели сначала обновляет
панель. Если правке нужно новое в core, это выпуск панели с поднятыми версиями модулей.

### Версии

- Источник истины — `module-versions.json` в корне репозитория: `{ "<id>": "X.Y.Z" }`. Файл живёт вне
  `xkeen-ui/`, поэтому его правка не меняет файлы core. В архив панели попадает сгенерированная копия.
- Стартовые версии — `1.0.0` у всех модулей (моё решение, совпадает с нынешней заглушкой).
- Версия поднимается при изменении поведения модуля, а не при смене байтов: файлы модулей могут меняться из-за
  имён чанков core. Сравнивать версии можно только в пределах одной панели.
- Версия установленного модуля хранится в `module-installed.json`. Формат расширяется обратно совместимо:
  `read_installed_modules` уже принимает словарь и список. Отсутствие версии читается как версия из
  `module-versions.json` панели.
- `MODULE_DEFINITIONS.version` и экран модулей показывают установленную версию.
- `core` своей версии не имеет, его версия — версия панели.

### Разрез сборки

- Граница core → модуль и модуль → модуль на фронте проходит только через динамический
  `import('xk-module/<id>')`. Статический импорт через границу запрещён: при отсутствии модуля падала бы вся
  страница.
- Граница модуль → core идёт через постоянные имена `xk-core/<путь>` с самого начала (вывод пробы Mihomo). Core
  публикует их как входы своей сборки, модуль считает внешними. Пока страницы идут через мосты к исходникам,
  importmap направляет `xk-core/` в `/static/`, чтобы модуль и страница использовали одну копию состояния.
  Так модуль не дублирует общий код и не содержит хэшированных имён файлов core.
- Статические импорты core → модуль (у Mihomo 12) переводятся на динамические при отделении модуля.
- `vite.config.mjs` считает `xk-module/*` внешними. Модуль собирается отдельным проходом: вход из описания
  модуля, вывод в `static/frontend-build/modules/<id>/`, манифест `.vite/module.<id>.json`.
- `npm run frontend:build` собирает панель и все отделённые модули. Команда должна остаться единственной.
- Importmap строится на сервере, в том же блоке, что `_codemirror6_importmap.html`, из манифестов
  установленных модулей. Отсутствующий или выключенный модуль в карту не попадает.
- `_IMMUTABLE_ASSET_ROOTS` включает `frontend-build/modules/`, у файлов модулей есть `.gz`.
- Манифесты модуля принадлежат модулю. `rebuild_frontend_manifests` и `_MANIFEST_PATHS` их не трогают.
- `panel.diagnostics.bundle.js` и аналоги остаются в core: это точка входа, она не меняется при правках модуля.
- Если страница открыта во время обновления, старый файл исчезнет и импорт упадёт. Это покрывает существующее
  сообщение о сбое загрузки с кнопками «Повторить» и «Обновить страницу».

### Каталог обновлений

Отдельные GitHub Releases для модулей не используются: `releases/latest` и список пререлизов забились бы ими, а
`parse_latest_prerelease` смотрит только 10 последних выпусков.

Файлы лежат в GitHub Release панели `V` рядом с её ассетами:

- `module-updates.json` и подпись `module-updates.json.sig`;
- `xkeen-module-<id>-<версия>.tar.gz` и `.sha256`.

Ассеты добавляются `gh release upload`. URL строит `official_release_asset_url`, адрес не меняется, API GitHub
для чтения файла не нужен. Проверено 01.11.2026: у выпусков `immutable=false`. Если включить неизменяемые
выпуски в настройках репозитория, схема перестанет работать.

Содержимое `module-updates.json`:

```json
{
  "kind": "xkeen-module-updates",
  "schema_version": 1,
  "panel_version": "3.1.0",
  "serial": 3,
  "modules": [ { "id": "...", "version": "...", "archive": "...", "size": 0, "sha256": "...",
                 "signing_key_id": "release-2026", "min_core": "3.1.0", "requires": [],
                 "conflicts": [], "requires_restart": true, "architectures": [] } ]
}
```

- Подпись тем же ключом и конвертом, что `catalog.json.sig`.
- Поле `kind` не даёт подставить подпись другого документа.
- `serial` растёт с каждой публикацией. Клиент хранит наибольший проверенный `serial` для своей панели и
  отвергает меньший.
- `panel_version` обязан равняться установленной версии панели.
- 404 — нормальное состояние, обновлений нет. Ошибка сети использует кэш по тем же правилам, что каталог:
  86400 секунд свежий, устаревший только при сбое транспорта.
- На одну панель в каталоге одна запись на модуль, новейшая.

### Обновление на роутере

- `OPERATIONS` получает `update`: module-only транзакция, тот же журнал, запуск, проверка здоровья, откат.
- Новейшая версия для панели — запись каталога обновлений, иначе запись `catalog.json` выпуска.
  `install`, `repair` и `update` берут именно её, поэтому `repair` не откатывает выпущенную правку.
- `update_available` истинно, если запись новее установленной версии.
- `module-ownership.json` принадлежит core и не меняется, а имена файлов модуля меняются. Фактическая
  принадлежность — карта панели плюс `module-ownership-overrides.json` в каталоге состояния, запись
  заменяет список файлов модуля. Её читают `plan.py`, `repair`, `remove`, `panel-update`, `profile-transition`.
- Обновление удаляет файлы прежней версии модуля по этой карте.
- `panel-update` заменяет модули и очищает overrides и версии.
- Копия для возврата панели становится устаревшей после обновления модуля, как и после любой операции
  с модулями (`previous_version.py`). Возврат панели в этом случае не предлагается (моё решение).
- Плохой выпуск исправляется следующим выпуском с более высокой версией. Отдельного отзыва на этапе 1 нет
  (моё решение: для него нужны ручной workflow и новое состояние модуля).
- Установщик и архив `xkeen-ui-routing.tar.gz` ставят базовые версии. Обновления видны уже в панели.

### Интерфейс

- На странице модулей у модуля версия, при наличии обновления — кнопка «Обновить» и окно операции как у `repair`.
- Вид окна согласуется макетами с настоящей панели до кода, как принято в проекте.
- Центр уведомлений сообщает об обновлениях модулей через `notification_catalog`.

### Выпуск модуля

Процедура для разработчика:

1. Ветка `module/<id>-<версия>` от тега панели `V`, потому что в `pre-release` core уже другой.
2. Правка только файлов модуля, подъём версии в `module-versions.json`, тесты и `npm run e2e:gate`.
3. Тег `module-<id>-X.Y.Z` на этом коммите. Тег не начинается с `v`, поэтому не затрагивает
   `check_release_tag.py` и сборку панели.
4. Workflow `release-module.yml` проверяет и публикует.
5. Ветка вливается в `pre-release` через `git merge`, не rebase.

Проверки CI, каждая останавливает выпуск:

- тег соответствует `module-versions.json`, версия выше выданных для этой панели;
- `V` определяется как ближайший тег-предок выпуска панели, у него есть GitHub Release;
- `V` — последняя опубликованная панель своего канала;
- продуктовые исходники изменены только в файлах модуля; вне `xkeen-ui/` разрешены `module-versions.json`,
  `tests/`, `e2e/` и `docs/`;
- результат сборки вне модуля совпадает с файлами архива панели `V` (правила ниже);
- pytest и проверки контракта пакета.

Сравнение с архивом панели (моё решение: сторож должен быть строгим, но выполнимым):

- байт в байт сравниваются все файлы core и соседних модулей, кроме перечисленных здесь;
- `module-ownership.json` и `module-sizes.json` сравниваются по смыслу: отличаться может только запись выпускаемого
  модуля. На роутер они не попадают, актуальный список файлов модуля даёт его архив и overrides;
- `BUILD.json`, копия `module-versions.json`, `retired-files.json` и зеркала Entware, взятые при сборке, в сравнении
  не участвуют. Модуль сам их не меняет;
- новый файл, не попавший в этот список, останавливает выпуск: список пополняют явно.

Если проверка «вне модуля» не проходит, правка уходит в выпуск панели. Это штатный исход, а не сбой.

`pre-push` требует отметку e2e и для `module-*`. Беты модулей отдельно не выпускаются: каталог лежит у конкретной
панели, поэтому правка для беты собирается от тега беты и доступна только на ней.

Проверки при выпуске панели:

- версия модуля в `module-versions.json` не ниже всех выданных тегов `module-<id>-*`: ловит забытое вливание;
- если исходники модуля менялись с прошлого выпуска панели, версия поднята. Скрипт перечисляет такие модули.

### Границы core

- Страница DevTools переходит в core (решение владельца, 01.11.2026): это основная страница настроек панели, и на ней
  лежит интерфейс обновления панели, а диагностика — необязательная часть. Это `templates/devtools.html`,
  `devtools.entry.js`, `static/js/features/devtools/*`, `routes/devtools.py` и всё, что им нужно. Выпуск модуля больше
  не может сломать экран обновления панели, а профили без диагностики получают DevTools.
- `tool.advanced-diagnostics` — это окно диагностики (`static/js/features/resource_monitor*`) и сбор истории
  (`routes/system_resources.py`, `services/system_resources_history/*`, кроме файлов, нужных core). Метки установки
  `INSTALL_MARKERS` и `_MODULE_INSTALL_MARKERS` меняются на файлы этой части, сейчас это `routes/devtools.py` и
  `templates/devtools.html`. Без модуля страница DevTools работает, а его вкладки и вход в окно скрыты.
- Описание модуля в реестре и профили приводятся в соответствие.
- Классификатор `owner()` и `_PACKAGE_OWNER_OVERRIDES` приводятся в соответствие: окно диагностики принадлежит
  `tool.advanced-diagnostics`.
- Новый сторож: файл с признаками модуля в core отклоняет тест, исключения перечислены явно.
- Сторож: статический импорт через границу модуля в исходниках и сборке отклоняется.

## Риски и проверки

- **Mihomo и Xray.** Отдельная сборка не знает хэшированных имён чанков core. Без мер общий код продублировался бы
  в модуле, а у общих объектов с состоянием появились бы две копии. Проба Mihomo подтвердила решение через `xk-core/*`.
  Xray отдельно не проверялся. Список `xk-core/*` становится поверхностью, которую нельзя переименовывать незаметно.
- **Обновление со старых панелей.** Старый код `panel-update` и `panel_package_contract` должны принять новый
  архив. Нужен тест на архиве от предыдущего стабильного выпуска и проверка на роутере.
- **Воспроизводимость в CI.** Замерена только локально. Проверка «байт в байт» требует одинаковых Node и
  `package-lock.json` при выпуске панели и модуля. Если зависимости ветки разошлись с тегом, выпуск остановится.
- **Отключённый и удалённый модуль.** Сейчас в пробе страница упала бы без манифеста модуля.
- **Смена принадлежности DevTools на установленных роутерах.** Метка установки модуля меняется, а `panel-update`
  должен верно определить набор модулей, в том числе на профилях без диагностики. Покрыть тестом перехода со старой панели.
- **Малая доля правок.** Правки в общем серверном коде остаются выпуском панели. Польза растёт по мере отделения.
- **Ключ подписи в новом workflow.** Доступ к секрету расширяется на теги `module-*`.
- **Реестр профилей.** Смена профиля после обновления модуля: `profile-transition` строит цель из архива панели и
  не должен откатывать модуль. Покрыть тестом.

## Отделение Xray (дополнение 04.11.2026)

Шаг 9 для `engine.xray`. Шаг 8 пройден на деле: диагностика выпускалась отдельно трижды (1.0.2, 1.0.5; 1.0.1 выдан
без публикации).

### Что показала проба

Проба 04.11.2026 на `a71d4c06` в отдельной копии, код не переносится:

- Связи исходников: Xray (45 файлов) → снаружи — 43 импорта к 21 файлу, снаружи → Xray — 27 импортов к 11 файлам.
  Статические снаружи: `github.js`, `dat_contents_modal.js`, `local_io.js`, `config_shell.shared.js`, мёртвый
  реэкспорт `features/index.js`.
- Правка строки в `routing.js` изменила 0 файлов вне модуля; правка `xkeen_runtime.js` и `panel.module_loader.js` —
  0 файлов модуля. Модулю нужны 20 файлов core через `xk-core/*`. JS сборки +0,8 %, модуль 910 КБ, общий код не
  задублирован. Полный e2e с разрезом и на чистом `HEAD` — 855 passed / 15 skipped / 0 failed.
- pytest пробы: 10 падений, все ожидаемые — сторожа прежнего устройства и описи.
- Классификатор `owner()` делит файлы сборки по словам в имени и отдал Xray три файла core. Без Xray пропал бы
  `xray_log_line_class`, нужный диагностике.
- Принадлежность считают два места, и для Xray они расходятся: `owner()` относит `github.js`, `local_io.js`,
  `config_shell.shared.js`, `dat_contents_modal.js` к core, `_PACKAGE_OWNER_OVERRIDES` — к Xray.

### Решённое устройство

- **Состав модуля** — файлы `static/js` с владельцем `engine.xray` по карте пакета (`build_module_ownership`), плюс
  `pages/logs_shell.shared.js` (его зовёт только Xray, в `_PACKAGE_OWNER_OVERRIDES`). Сторож границ берёт владельцев
  из этой карты, а не из `owner()`. `owner()` для исходников не меняется: две карты расходятся и у редакторов, Mihomo,
  терминала, а после разреза исходников Xray в манифесте core нет, так что роутеру его ответ для них не нужен.
- **Вход** — `js/pages/xray.module.entry.js`, единственный вход сборки модуля. Экспорт:
  `activate(context)` и `load(part)`. Части: `bundle`, `routing`, `routing_cards`, `routing_shell`,
  `routing_templates`, `inbounds`, `outbounds`, `xray_logs`, `xray_preflight_modal`, `github`, `dat_contents`.
  Нынешний `panel.routing.bundle.js` переезжает в модуль как `xray.module.bundle.js`. На его месте в core остаётся
  загрузчик в несколько строк с тем же ключом `panel-routing`.
- **Core → модуль** — общий мостик core `js/features/module_parts.js`: `loadModulePart(moduleId, part)`,
  `loadedModulePart(moduleId, part)`, `rememberModulePart(moduleId, part, mod)`. Имя без слов модулей. Все
  импорты core → Xray идут через него, в том числе ленивые загрузчики `github` и `datContents`.
- **Модуль → core** — в исходниках модуля имена `xk-core/<путь>`, не относительные пути. Сторож
  `test_no_static_import_crosses_a_separated_module_boundary` это уже требует. Importmap отдаёт префикс
  `xk-core/` → `/static/` и при наличии сборки: страницы пока исполняют исходники через мосты. Node-тесты JS Xray
  получают такой же резолвер (`--import` с хуком).
- **Поверхность `xk-core`** — все `xk-core/<путь>`, найденные в `static/js`, становятся входами основной сборки
  (`CORE_PUBLIC_ENTRIES` вычисляется, а не пишется руками), `preserveEntrySignatures: 'strict'`. Эти входы пока
  не используются во время работы и пригодятся при переходе страниц на сборку. Обязательные статические зависимости
  поверхности есть в любом установленном профиле и варианте редактора с `engine.xray`; часть принадлежит `tool.editor`.
  Установщик включает зависимости по статическим импортам `xk-core/` оставляемых файлов сборки, динамические не
  замыкает: необязательные `prettier_loader.js` и `schema_quickfixes.js` могут отсутствовать в light-варианте.
- **Имена в сборке** — после отделения файлы Xray есть только в `frontend-build/modules/engine.xray/`. Правила
  `owner()` «xray/routing/inbounds/outbounds в имени файла сборки» и `panel.routing.bundle` для `assets/` снимаются.
  Сторож: в `manifest.build.json` нет исходников модуля.
- **Сбой загрузки** — файл модуля, пропавший при обновлении, даёт штатное сообщение «Обновить страницу». Повтор
  невозможен: браузер запоминает упавший импорт по имени.
- **Python не меняется.** Отдельный выпуск Xray везёт его Python-файлы по карте пакета. Правка в общем серверном
  коде, как и раньше, — выпуск панели.
- **Версии.** Коммит разреза меняет файлы Xray, резервных копий и редакторов (`backups.js`, `json_editor_modal.js`).
  Поднимаются `engine.xray`, `tool.backups`, `tool.editor`, иначе проверка выпуска панели остановит тег.
- **Первый отдельный выпуск Xray** — только от панели, которая сама несёт разрез и последняя в своём канале.

### Риски

- Профиль без Xray (`mihomo-minimal`): ни одного запроса к `xk-module/engine.xray` и ни одной ошибки в консоли. Покрыть
  e2e по образцу `diagnostics_module_absent.spec.mjs` и тестом профилей установки.
- Выключенный модуль Xray при установленном ядре Xray: экран Xray не открывается, панель работает.
- Поверхность `xk-core` растёт с каждым модулем. Переименование файла в ней — выпуск панели и всех модулей, которые его зовут.
  Сторож перечисляет поверхность явно, правка списка видна в ревью.
- Модуль, собранный от старого core, не знает новых путей `xk-core`. Это закрыто правилом «только последняя панель
  канала».

### Решения Claude, которые стоит проверить владельцу

- `xk-core/…` прямо в исходниках модуля, а не подмена путей плагином сборки, как в пробе. Граница видна в коде, сторож
  уже есть, сборка не зависит от классификатора. Цена: правка ~37 импортов и резолвер для node-тестов.
- Один вход с `load(part)` вместо нескольких входов модуля: importmap и манифест уже рассчитаны на один вход.
- `github.js` и окно содержимого `.dat` уходят в модуль Xray, как уже записано в карте пакета.
