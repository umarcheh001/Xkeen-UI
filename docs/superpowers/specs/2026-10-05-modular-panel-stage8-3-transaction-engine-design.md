# Stage 8.3: transaction/updater engine

## Цель

Добавить core-owned движок, который из проверенного архива официального модуля
делает установленный, переустановленный или удалённый модуль и возвращает
панель в прежнее состояние при любой ошибке — в том числе когда панель после
перезапуска не поднялась или питание пропало посреди операции.

Движок получает на вход проверенный каталог и архив от клиента Этапа 8.2 и
отдаёт Этапу 8.4 три вещи: план операции, запуск операции и её состояние.

## Scope

Подэтап включает:

- планировщик операций `install`, `remove`, `repair` для одного модуля;
- журнал операции с копией заменяемых файлов и откатом;
- отдельный процесс-исполнитель, не зависящий от процесса панели;
- проверку запуска панели после перезапуска и автоматический откат;
- доигрывание прерванной операции при загрузке роутера;
- карту владения файлами в составе панели;
- предсжатые копии статики в пакетах модулей;
- подключение Monaco по требованию на страницах `/backups` и
  `/mihomo_generator` и тест сборки «пакет поверх профиля установщика»;
- запрос каталога конкретного релиза в клиенте каталога;
- сосуществование с `install.sh` и профилями Этапа 7;
- правку контракта Этапа 8.0 в части топологии;
- unit-, integration-тесты и приёмку на роутере.

## Non-goals

Подэтап не добавляет Flask routes, UI, уведомления, обновление всей панели и
смену профиля (8.4–8.7). Он не обновляет модуль до версии, отличной от версии
панели, не меняет вариант редактора, не исполняет скрипты из архива и не
принимает архивы не из официального каталога.

## Принятые решения

Четыре решения согласованы 5 октября 2026 года и определяют остальной дизайн.

### 1. Файлы модуля лежат в общем корне панели

Контракт 8.0 описывал `modules/<module-id>/<version>/` и указатель `current`.
Панель из такой раскладки загружаться не умеет: Python-импорты, статика,
шаблоны, предсжатые `.gz` и frontend manifest читаются из корня установки.
Переделка загрузки затронула бы каждый запуск панели и потребовала бы
физической миграции каждой установки.

Поэтому payload модуля раскладывается в `/opt/etc/xkeen-ui` по путям из
manifest. Атомарность одного `rename` заменяется журналом операции с копией
заменяемых файлов; все модули контракта и так требуют перезапуска, и новые
файлы начинают действовать только после него. Раздел «Топология будущих
пакетов» контракта 8.0 переписывается (см. «Правка контракта»).

### 2. Операцию ведёт отдельный процесс, init-скрипт доигрывает обрыв

Панель только запускает исполнитель оторванным процессом и читает его файл
состояния — по образцу самообновления. Исполнитель сам перезапускает панель,
ждёт её ответа и подтверждает операцию либо откатывает её. Если питание
пропало посреди операции, init-скрипт перед стартом панели видит незавершённый
журнал и вызывает восстановление.

### 3. Версия модуля равна версии установленной панели

Все пакеты режутся из одного дерева и получают версию релиза; сочетание
«модуль новее ядра» никем не собирается и не проверяется, а `min_core`
сборщик заполняет константой. В 8.3 модуль ставится только из релиза, версия
которого совпадает с версией панели из `BUILD.json`. Переход на новую версию
происходит вместе с панелью (8.5). Правило совместимости — одна функция
планировщика; ослабить его можно позже без изменения движка.

Следствие: каталог нужен для установленной версии, а не для последней.
Сборки без semver-версии (локальный архив с хэшем коммита) модульных операций
не поддерживают и получают `panel_version_unsupported`.

### 4. Состав модуля определяют manifest пакетов, установщик не меняется

`install.sh` выбирает файлы профиля по своим правилам (`owner()` и замыкания),
и на урезанных профилях его набор расходится с пакетами: замер 5 октября —
141 файл пакетов не установлен (в основном Monaco лёгкого варианта редактора),
33–36 установленных файлов принадлежат пакетам невыбранных модулей. При равных
версиях это движку не мешает: он либо кладёт файлы с тем же содержимым, либо
удаляет ровно список модуля.

Чтобы удалить или починить модуль, поставленный установщиком, без сети, панель
везёт карту владения `module-ownership.json`. Перевод установщика на ту же
карту — отдельная работа, записана долгом к 8.5.

## Компоненты

| Компонент | Файл | Ответственность |
| --- | --- | --- |
| Планировщик | `services/module_transactions/plan.py` | Решает, допустима ли операция, и строит план. Ничего не пишет. |
| Журнал | `services/module_transactions/journal.py` | Каталог операции, копия заменяемых файлов, запись шагов, откат. |
| Состояние | `services/module_transactions/state.py` | Чтение и атомарная запись `status.json`, замок операции. |
| Исполнитель | `scripts/module_transaction.py` | Команды `run`, `recover`, `status`. Ведёт операцию целиком. |
| Запуск | `services/module_transactions/launcher.py` | Создаёт операцию, запускает исполнитель оторванным процессом. |
| Карта владения | `module-ownership.json` | Пишет сборщик релиза, читает планировщик. |
| Init-скрипт | шаблон в `install.sh` | Перед стартом панели вызывает `recover`, если есть журнал. |

Исполнитель не импортирует Flask, `app_factory` и `routes`: он обязан
запускаться, когда панель сломана. Ему доступны планировщик, журнал, состояние,
`module_package_contract`, `module_catalog_client`, `module_catalog_trust` и
чтение/запись `modules.json` без запуска registry-потоков. Все эти файлы
принадлежат пакету `core`.

Интерфейсы между частями:

- `build_plan(operation, module_id, *, panel_root, state_dir, catalog) -> Plan`
  либо `ModuleTransactionError(code, message, details)`;
- `Plan` — неизменяемый: `operation`, `module_id`, `version`, `files_add`,
  `files_remove`, `archive` (имя, размер, SHA-256 либо `None` для удаления),
  `required_free_bytes`, `restart_required`, `installed_after` (состав
  установленных модулей после операции);
- `launch(plan) -> operation_id` и `read_status() -> dict`;
- `module_transaction.py run --operation <id>` выполняет план из
  `operation.json`; `recover` не принимает аргументов.

## Данные на диске

| Путь | Назначение |
| --- | --- |
| `/opt/etc/xkeen-ui/` | Файлы модулей в общем корне, как сейчас. |
| `/opt/etc/xkeen-ui/module-ownership.json` | Карта «модуль → список файлов» для версии панели. |
| `/opt/etc/xkeen-ui.module-transactions/<operation-id>/` | Каталог операции на той же файловой системе, что и панель. |
| `…/<operation-id>/operation.json` | План, текущий шаг, список уже выполненных действий. |
| `…/<operation-id>/staging/` | Скачанный архив и распакованный payload. |
| `…/<operation-id>/backup/` | Заменённые и удалённые файлы, копии state-файлов. |
| `<ui_state_dir>/module-operations/status.json` | Состояние текущей и итог последней операции для панели. |
| `<ui_state_dir>/module-catalog/catalog-<version>.json` | Проверенный каталог конкретного релиза. |

Отдельного реестра версий нет: при равенстве версий версия модуля — это версия
панели, а признак «установлен» остаётся в `module-installed.json`, который
registry уже читает. После подтверждения каталог операции удаляется целиком;
после отката — тоже. Единственное, что переживает операцию, — `status.json`
с её итогом.

`operation-id` — время UTC и случайный суффикс
(`20261005T181500Z-3f9a1c`). Одновременно существует не более одного каталога
операции; посторонние каталоги удаляются при старте следующей операции после
`recover`.

## Карта владения

`scripts/build_modular_panel_release.py` уже вычисляет владение
(`build_module_ownership`) для module archives. Тот же результат он
записывает в `module-ownership.json`:

```json
{
  "schema_version": 1,
  "modules": {
    "tool.backups": ["templates/backups.html", "…"]
  },
  "frontend": {
    "bridge": { "…": "полный .vite/manifest.json" },
    "build": { "…": "полный .vite/manifest.build.json" }
  }
}
```

Файл попадает в panel archive и в legacy bootstrap archive
`xkeen-ui-routing.tar.gz`, принадлежит `core` и входит в managed-набор
установщика. В репозиторий он не коммитится: в нём имена чанков сборки с
хэшами содержимого. Сборка без карты (локальный архив без сборщика) модульных
операций не поддерживает: все три отклоняются с
`module_ownership_unavailable`.

Чтобы карта и пакеты описывали одно и то же дерево, CI собирает module
archives из `package-root` — того же каталога, из которого упакован bootstrap
archive, уже со сжатой статикой и с записанной картой.

### Пакет поверх урезанного профиля

Пакет самодостаточен вместе с пакетами своих зависимостей, но установщик
урезанного профиля ставит эти пакеты не целиком: лёгкий вариант редактора не
содержит Monaco. Замер 5 октября нашёл два оборванных статических импорта при
раскладке пакета поверх `xray-minimal`:

- `tool.backups`: `backups.screen.bootstrap.js` →
  `static/js/ui/monaco_loader.js`;
- `engine.mihomo`: `mihomo_generator.screen.bootstrap.js` →
  `static/js/pages/editor_monaco.shared.js`.

Причина — в двух отдельных страницах, а не в пакетах. Главная панель после
Этапа 6 подключает Monaco по требованию и только там, где он установлен, а
страницы `/backups` и `/mihomo_generator` импортируют его поддержку
статически при открытии, хотя Monaco нужен им лишь при переключении движка
редактора.

Решение — убрать причину: обе страницы подключают Monaco тем же ленивым путём,
что и главная панель (`panel.editor.monaco.bundle.js` через проверку
возможностей редактора), а при его отсутствии остаются на CodeMirror. Движок
ничего не докладывает из чужих пакетов.

Чтобы такая связь не появилась снова, добавляется тест сборки: пакет каждого
необязательного модуля, разложенный поверх каждого профиля установщика, в
который входят его зависимости, не оставляет ни одного оборванного
статического импорта — ни JS, ни Python.

### Manifest сборки фронтенда

`static/frontend-build/.vite/manifest.json` и `manifest.build.json`
принадлежат `core`, но установщик урезанного профиля оставляет в них только
записи выбранных модулей: в `xray-minimal` нет записей мостов `backups`,
`devtools` и `mihomo_generator`. Без записи страница установленного модуля не
найдёт свой мост.

Карта хранит оба manifest целиком. После шага `applying` исполнитель
пересобирает их: запись остаётся, если её `file` существует на диске, а её
`imports` и `dynamicImports` сокращаются до оставшихся записей. Оба файла
копируются в `backup/` и возвращаются при откате как state-файлы. На
нетронутой установке любого профиля пересборка обязана давать ровно те
manifest, которые записал установщик, — на это отдельный тест.

## Операции и правила планировщика

| Операция | Что делает | Отклоняется, если |
| --- | --- | --- |
| `install` | Кладёт файлы пакета, отмечает модуль установленным и включённым. | Модуль уже установлен; не установлена зависимость; конфликт; нет места. |
| `repair` | Заново кладёт файлы пакета установленного модуля. | Модуль не установлен. |
| `remove` | Убирает файлы модуля, отмечает выключенным и неустановленным. | От модуля зависит установленный модуль; модуль — работающий движок. |

Общие правила:

- `core` нельзя устанавливать, удалять и чинить этой операцией;
- `tool.editor` можно только чинить: он зависимость обоих движков, а смена
  варианта редактора остаётся за Этапом 6/7;
- версия записи каталога обязана равняться версии панели, архитектура —
  результату `detect_platform_architecture()`;
- зависимости и конфликты берутся из каталога и сверяются с
  `module-installed.json`; зависимости автоматически не ставятся и не
  удаляются;
- удаление движка, чей процесс сейчас работает, отклоняется с
  `module_engine_active` — тем же условием, которым registry запрещает его
  отключение;
- пользовательские данные (`_user_owned` Этапа 7, state-файлы, конфигурации
  ядер) не входят ни в `files_add`, ни в `files_remove`;
- путь из manifest, который по карте владения принадлежит другому модулю,
  — ошибка `module_ownership_conflict` до любых изменений.

Свободное место: размер архива + размер payload + размер заменяемых и
удаляемых файлов (если копию не удалось сделать жёсткой ссылкой) + 20 %.
Проверка выполняется по файловой системе каталога операции.

## Ход операции

Состояние записывается в `operation.json` атомарно перед каждым шагом.

| Шаг | Действие | Что изменено в корне |
| --- | --- | --- |
| `prepared` | Создан каталог операции, записан план, взят замок. | Ничего. |
| `downloading` | Архив скачан `download_verified_archive` в `staging/`. | Ничего. |
| `verifying` | `validate_module_archive`, сверка manifest с планом, распаковка в `staging/payload/` только regular files с повторной проверкой пути. | Ничего. |
| `applying` | Для каждого файла: копия прежнего в `backup/`, затем `os.replace` из staging. Для удаляемого — перенос в `backup/`. Каждый файл отмечается в журнале после выполнения. | Файлы модуля. |
| `state` | Копия и обновление `module-installed.json`, `modules.json`, `install-profile.json`, `install-managed.json`. | State-файлы. |
| `restarting` | `init-скрипт restart`. | — |
| `health` | Ожидание ответа панели и проверка модуля. | — |
| `committed` | Каталог операции удалён, замок снят, итог в `status.json`. | — |

Копия прежнего файла делается жёсткой ссылкой, при неудаче — копированием.
Новый файл сначала копируется рядом с целью под временным именем
(`<имя>.xk-tx-new`), затем `os.replace` — отдельный файл никогда не бывает
наполовину записанным.

### Предсжатые копии статики

Сегодня `.gz` есть только в legacy bootstrap archive: CI сжимает статику в
`package-root/xkeen-ui`, а module archives собираются из корня репозитория,
где `.gz` нет. Модуль, поставленный из такого пакета, отдавался бы без сжатия.

Поэтому module archives собираются из того же `package-root`, где статика
уже сжата `precompress_static_assets` (те же расширения, порог размера и
исключения, что у bootstrap archive). Сборщик владения относит `<имя>.gz` к
тому же модулю, что и `<имя>`, — после замыкания по импортам, а не по
правилам имён. Такой файл входит в manifest пакета, в `module-ownership.json`
и в panel archive. Сжатие детерминировано, так что воспроизводимость релиза
сохраняется.

Исполнитель кладёт и убирает `.gz` как обычные файлы пакета, а после шага
`applying` выравнивает время изменения пары: панель отдаёт предсжатую копию,
только если она не старше исходника. `.gz` без исходника или с исходником,
которого в пакете нет, на диске не остаётся.

Для `remove` шагов `downloading` и `verifying` нет.

### Проверка запуска

После `restart` исполнитель до 120 секунд (переопределяется
`XKEEN_UI_MODULE_TX_HEALTH_TIMEOUT`) ждёт, пока:

1. `GET http://127.0.0.1:<порт>/api/auth/status` отвечает `200`;
2. в `modules.json` у модуля операции нет `last_error` (для `install` и
   `repair`).

Адрес проверки передаёт панель при запуске операции: она знает свой порт.
Невыполнение любого условия за отведённое время — откат.

Перезапуск панели исполнителем идёт через init-скрипт, а тот перед стартом
вызывает `recover`. Чтобы восстановление не откатило операцию, которая как
раз выполняется, `recover` ничего не делает, пока жив процесс исполнителя,
записанный в `operation.json`.

### Откат

Откат читает журнал с конца: возвращает state-файлы из копий, удаляет
добавленные файлы, возвращает заменённые и удалённые из `backup/`,
перезапускает панель и записывает в `status.json` итог `rolled_back` с кодом
причины. Каждое действие идемпотентно: повторный откат после обрыва даёт тот
же результат.

### Неудачный откат

У отката два разных плохих исхода, и они различаются в `status.json`.

**Файлы возвращены, но панель не отвечает** — итог `rolled_back`, признак
`panel_unresponsive: true`. Дерево панели уже прежнее, причина вне операции
(занятый порт, медленный накопитель, не хватило времени ожидания). Движку
делать больше нечего: каталог операции удаляется, новые операции не
блокируются. Пока панель не отвечает, запускать их всё равно некому.

**Файлы вернуть не удалось** — итог `rollback_failed`. Это ошибка
файловой системы: накопитель отключился или перешёл в режим только для
чтения, ошибка ввода-вывода, повреждена копия. Тогда:

- исполнитель останавливается на первом файле, который не удалось вернуть,
  и записывает в `status.json` путь и текст ошибки; уже возвращённые файлы
  остаются возвращёнными;
- каталог операции с `backup/` сохраняется: в нём единственные копии
  прежних файлов;
- панель всё равно перезапускается — на случай, если она работоспособна и
  в смешанном состоянии;
- планировщик отклоняет новые операции с `operation_rollback_failed`, пока
  каталог существует: поверх смеси версий раскладывать нельзя.

Выходы из `rollback_failed`:

1. повторный `module_transaction.py recover` — вручную, кнопкой «Повторить
   откат» (API 8.4) или сам при следующей загрузке роутера; откат
   идемпотентен и продолжает с места остановки;
2. `install.sh`: сначала вызывает `recover`, при повторной неудаче ставит
   панель из архива по сохранённому профилю — это перезаписывает все
   управляемые файлы — и после успешного запуска удаляет каталог операции.

Пользовательские данные и конфигурации ядер в операции не участвуют и ни при
каком исходе не меняются.

### Обрыв на каждом шаге

| Обрыв на шаге | Что на диске | Что делает `recover` |
| --- | --- | --- |
| `prepared`, `downloading`, `verifying` | Корень не тронут. | Удаляет каталог операции. Итог `interrupted`. |
| `applying`, `state` | Часть файлов новая. | Откат по журналу. Итог `rolled_back`. |
| `restarting`, `health` | Всё новое, не подтверждено. | Откат по журналу: неподтверждённая операция считается невыполненной. |
| откат | Часть возвращена. | Продолжает откат. |
| `committed` до удаления каталога | Всё новое, подтверждено. | Удаляет каталог операции. |

`recover` при загрузке панель не перезапускает и её ответа не ждёт: init-скрипт
запускает панель сразу после него. Ожидание в init-скрипте задерживало бы
`rc.unslung`.

Init-скрипт вызывает `recover`, только если каталог
`/opt/etc/xkeen-ui.module-transactions` непуст; без него это одна проверка в
оболочке, Python не стартует.

Сигнал `SIGTERM` исполнителю до шага `applying` завершает операцию без
изменений, начиная с `applying` — запускает откат. Отмена из панели (8.4)
использует этот же путь.

## Сосуществование с `install.sh` и самообновлением

- Замок операции общий с самообновлением панели (`lock` в каталоге
  обновления, `services/self_update/state.try_acquire_lock`): модульная
  операция и обновление панели не идут одновременно.
- `install.sh` перед применением профиля вызывает
  `module_transaction.py recover`, если каталог операций непуст и исполнитель
  существует в установленной панели.
- После успешной операции профиль в `modules.json` и `install-profile.json`
  становится `custom` с фактическим списком модулей — иначе следующее
  обновление прочитает сохранённый пресет и вернёт прежний состав.
- Добавленные файлы дописываются в `install-managed.json`, удалённые —
  убираются из него: установщик продолжает управлять ими при обновлении.
- `module-installed.json` получает явное значение для модуля; маркер-файлы
  остаются запасным признаком.

## Изменение клиента каталога

`ModuleCatalogClient` получает `get_release_catalog(release_version)`: строит
адрес каталога и подписи через `official_release_asset_url`, проверяет их тем
же `_verified_snapshot` и кэширует в `catalog-<version>.json`. Релиз
неизменяем, поэтому такой кэш не устаревает и порог отката к нему не
применяется. `get_catalog()` для уведомлений о новых версиях не меняется.

## Ошибки

Все отказы — `ModuleTransactionError` со стабильным `code`. Ошибки клиента
каталога и контракта пакетов проходят со своими кодами без переименования.
Новые коды: `panel_version_unsupported`, `module_version_mismatch`,
`module_already_installed`, `module_not_installed`, `module_dependency_missing`,
`module_required_by`, `module_conflict`, `module_engine_active`,
`module_operation_forbidden`, `module_ownership_unavailable`,
`module_ownership_conflict`, `module_free_space`, `operation_in_progress`,
`operation_health_failed`, `operation_rollback_failed`.

`status.json` содержит `operation_id`, `operation`, `module_id`, `step`,
`result` (`running`, `committed`, `rolled_back`, `interrupted`,
`rollback_failed`), `error_code`, время начала и конца и журнал шагов для
человека. Тексты архива и каталога в журнал не попадают.

## Правка контракта 8.0

В `scripts/generate_modular_panel_stage8_contract.py` и производных
`docs/modular-panel-stage8-contract.{json,md}`:

- `payload_root` — `/opt/etc/xkeen-ui (ownership paths из manifest)`;
- `active_pointer` и `pointer_switch` заменяются на `apply` —
  `journaled per-file replace with backup`;
- `registry` — `module-installed.json + module-ownership.json`;
- `transaction_root` — `/opt/etc/xkeen-ui.module-transactions/<operation-id>/`;
- строка `module-only-file-diff` матрицы: «меняются только файлы из manifest
  выбранного модуля и state-файлы»;
- добавляется правило равенства версий модуля и панели.

`README-modular-panel-plan.md` и
`docs/modular-panel-stage8-official-module-manager.md` правятся в тех же местах;
подэтап 8.3 помечается закрытым после приёмки.

## Тестирование

Unit:

- планировщик — каждая строка таблицы операций и каждое общее правило;
- журнал — замена, добавление, удаление, идемпотентность отката;
- предсжатые копии — каждый `.gz` пакета лежит в том же модуле, что исходник,
  после операции копия не старше исходника и отдаётся панелью;
- распаковка — traversal, абсолютный путь, ссылка, файл вне manifest;
- запрос каталога релиза — подпись, несовпадение версии, кэш.

Integration (временный корень панели, поддельный transport, подменяемые
команда перезапуска и адрес проверки через env):

- `install` → `committed`: изменились только файлы manifest и state-файлы;
- `remove` → `committed`: остальные модули байт в байт прежние;
- сбой проверки запуска → `rolled_back`, дерево байт в байт прежнее;
- обрыв исполнителя на каждом шаге → `recover` даёт состояние из таблицы;
- несовпадение SHA-256 и размера → корень не тронут;
- профиль после операции — `custom`, повторный `apply_profile` Этапа 7 не
  возвращает удалённый модуль и не сносит установленный.

Тесты на Windows не требуют init-скрипта и жёстких ссылок: команда
перезапуска и проверка подменяются, копия падает обратно на копирование.

Поставляемый исполнитель не содержит тестовых параметров: источник релиза,
ключи проверки и обрыв на заданном шаге подменяет отдельный тестовый
запускатель из `tests/support/`, который в архив панели не входит.

Guardrail: исполнитель и `services/module_transactions/*` не импортируют
Flask и `routes` (проверка по AST), все их файлы принадлежат пакету `core`.

Приёмка на роутере (aarch64, затем MIPS):

1. установка `xray-minimal` из релизной сборки, `install tool.terminal`,
   терминал работает;
2. `remove tool.terminal`, панель чистая, 404 и ошибок консоли нет;
3. подложенный сломанный файл модуля → панель не поднимается → откат,
   прежняя панель отвечает;
4. отключение питания на шаге `applying` (kill исполнителя и перезагрузка) →
   после загрузки панель прежняя;
5. обновление панели `install.sh` после `install` модуля сохраняет состав.

## Долги и отложенное

- Перевод `install.sh` на карту владения пакетов и вариант редактора как
  отдельная сущность — к 8.5.
- Обновление модуля между релизами по честному `min_core` — после появления
  дисциплины выпуска.
- Хранение прежней версии модуля после подтверждения не делается: откат
  подтверждённой операции — это обратная операция.
