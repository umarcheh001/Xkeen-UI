# Завершение этапов 6–7 импорта узлов Mihomo

Дата: 28 октября 2026 года. Рабочая база: `pre-release`, `e8b7839b`.

## Основание и состояние

Владелец поручил завершить требования этапа 6 из
`README-mihomo-node-import-redesign-plan.md`, затем перейти к этапу 7.
Основной UX уже определён разделами 1, 5, 10 исходного плана.
Этот документ уточняет восстановление и границы операций; новый способ
парсинга или выдачи конфигураций не вводится.

Статус: владелец выбрал вариант А — отдельный шаг проверки. Реализация начата.

## Подтверждённые проблемы

- Повторное сохранение использует `_lastCandidate` и его старую файловую
  ревизию. Изменения редактора между сохранениями не попадают в новый запрос.
- Закрытие очищает результат/статус; job id не хранится как самостоятельная
  операция для восстановления наблюдения.
- Регистрация автообновления вызывается из commit модала, но черновик
  не переносит намерение регистрации в сохранение главным редактором.
- Блокировки модала и toolbar независимы.
- `/api/restart-job/<id>` возвращает `ok: true` для успешного чтения статуса;
  это не признак успешного завершения процесса. Модал проверяет `result.ok`,
  не проверяя exit code.
- Сводка строится при финальном действии; предварительный review полного
  конфига и отдельное сравнение с файлом отсутствуют.

Исследовательский harness и его фактические результаты:
`.superpowers/sdd/2026-10-28-mihomo-import-completion/`.
Endpoint записи в исследовании подменён; роутеры не используются.

## Варианты размещения проверки

**А, рекомендация:** отдельное состояние того же модала. Источник и группы
уступают место сводке, предупреждению о несохранённых правках и техническим
представлениям по раскрытию. «Назад» возвращает к результатам без нового
скачивания или выдачи Amnezia. Три финальных действия доступны после review.
Цена: один переход перед сохранением.

**Б:** сводка под настройками групп, всё в одном состоянии. Меньше переходов,
но длиннее окно и сложнее удерживать сводку/предупреждение рядом с действиями.

Оба варианта используют существующие Operator tokens, иконки и modal manager.
Макеты получены изменением DOM настоящей локальной панели; данные демонстрационные.
Изменять production UI до выбора владельца нельзя.

## Техническое решение

1. Подготовка создаёт неизменяемый snapshot: текст редактора, identity профиля,
   file baseline, outputs, группы, имя/назначение и параметры автообновления.
   Сводка, diff и сохранение используют один snapshot.
2. Перед действием и после асинхронной подготовки сверяются revision/context.
   Изменившийся контекст требует пересборки и повторного подтверждения.
   После save обновляются baseline и состояние операции; повторный save
   не вставляет узлы заново и не использует старую ревизию.
3. Общий adapter панели принимает явные content/action, владеет блокировкой,
   pending registrations и наблюдением restart job. Главный редактор и модал
   используют его; публичные facade и контракты других клиентов сохраняются.
4. Pending registration хранится в памяти страницы отдельно от открытого
   модала и активируется только после сохранения конфига, содержащего нужные
   узлы. Удалённые из черновика узлы не создают активную регистрацию.
   Успешные регистрации не повторяются; retry касается только неудачных.
5. Исход операции различает save failure, saved/apply failed, unknown,
   applied и registration warning. Для job проверяются terminal status,
   exit code и error; затем runtime Mihomo. API unavailable показывается
   отдельно от stopped. Polling ограничен по времени; job id сохраняется
   для восстановления. Само закрытие модала не отменяет серверный job.
6. Backend повторно сверяет файловую ревизию непосредственно перед записью
   и сериализует операции панели. Отсутствующая revision импорта не даёт
   незаметно отключить защиту. Отсутствующее ядро/неуспешная проверка не
   позволяют записать конфиг.
7. Этап 7 начинается с замеров first-open/parse/candidate и HTTP count для
   1/10/50 узлов. При подтверждении N-запросного bottleneck вводится batch
   patch уже распознанных outputs, без повторного fetch/Amnezia issuance;
   старый одиночный endpoint сохраняется.

## Приёмка

Поведенческие тесты проверяют stale editor/profile/file, concurrent actions,
черновик → toolbar save → registration, partial registration retry,
job exit 1 при `ok: true`, timeout и close/reopen. Независимо проверяются
draft/save-only/apply и отсутствие лишних записей/рестартов/выдач.
Frontend build предшествует E2E. Итоговые замеры сравниваются с baseline.
Темы dark/light, ширина 390 px и короткий экран проверяются визуально.

Релиз, push и установка на роутер требуют отдельных явных указаний владельца.
