# Понятное расписание подписок Xray: согласованные решения

Статус: реализация выполнена 29.10.2026; результаты проверок и ограничения —
в журнале `.superpowers/sdd/2026-10-28-xray-subscription-schedule-ui/progress.md`.

- Режим «Интервал» сохраняется, включая существующее поведение и значения.
- Режим «По расписанию» позволяет выбрать «Каждый день», «По дням недели»,
  «Раз в месяц» и последним пунктом «Своё расписание (для опытных)».
- В обычных вариантах пользователь выбирает время и, при необходимости, дни
  недели или число месяца. Форма составляет cron самостоятельно и показывает
  ближайшее обновление по времени роутера.
- В последнем пункте доступен ручной ввод cron с серверной проверкой и показом
  ближайшего обновления. Существующие сложные выражения сохраняются без изменений
  и открываются в этом пункте; переход между режимами не должен молча менять их.
- Блок и элементы формы выравниваются по ширине доступной области, в светлой и
  тёмной темах и на узком экране. Макеты лежат на рабочем столе в папке
  «Макеты расписания подписок»; выбран компактный вариант с пунктом в списке,
  а не отдельный раскрываемый блок для опытных пользователей.
- Подписки с выбранным календарным расписанием не участвуют в операции
  «Выровнять расписание»: вручную выбранное время сохраняется. Действующая
  функция уже исключает `schedule_mode == cron`; это правило нужно сохранить
  для всех графических вариантов, которые представляются через cron.
- Кнопка выравнивания остаётся полезной для других подписок в режиме интервала;
  если подходящих подписок нет, интерфейс должен объяснить, почему их нет.
- В списке выбран вариант А: под временем следующего обновления календарной
  подписки выводится подпись «По расписанию» и понятное описание повторения.
  Для интервальных подписок остаётся обозначение интервала. Макет —
  `variant-A.png` в папке «Макеты расписания подписок» на рабочем столе.
- Ошибку обновления показывать с понятной причиной, временем первого сбоя
  штатной попытки и датой последней успешной загрузки, когда данные доступны.
  Последующие ошибки не сбрасывают первый сбой; успех очищает предупреждение.
  Для старых записей не угадывать неизвестное время первого сбоя.

Детали редких дат, переключения существующих выражений и формулировок ошибок
нужно уточнить при проектировании реализации; существующее поведение не менять
молча. Для неизвестных ошибок используется безопасное общее описание,
чтобы исключение не показывало секреты адреса подписки.
