# Выбор источника ядер Xray и Mihomo

Дата: 30 сентября 2026. Статус: согласовано, ожидает плана реализации.

## Задача

XKeen UI сейчас показывает версии ядер и запускает обновление из раздела
«Команды». Установка делегируется штатным командам `xkeen -ux` и `xkeen -um`,
поэтому пользователь не может выбрать проверенный форк с другим набором
совместимостей.

Нужно добавить управляемый выбор источника отдельно для Xray и Mihomo, не
разрушая текущий командный интерфейс и сохраняя возможность безопасно вернуться
к официальному ядру.

Первая версия поддерживает только заранее проверенные профили. Установка
произвольного GitHub-репозитория является отдельным будущим advanced-сценарием и
в базовом UI не появляется.

## Принятые решения

- Основной UI выбора находится в модуле соответствующего движка:
  `engine.xray` и `engine.mihomo` получают одинаковый по структуре control, но
  независимые каталоги профилей.
- В разделе «Команды» остаются низкоуровневые `-ux` и `-um` для диагностики и
  совместимости. Основной сценарий выбора профиля и установки переезжает в
  экраны движков.
- Выбор профиля и установка разделены. Сохранение профиля не меняет бинарник.
- В первой версии доступен только последний stable-релиз профиля.
- Установка без подходящего asset или контрольной суммы запрещена.
- До замены бинарника автоматически сохраняются текущий бинарник и метаданные.
- Статус установленного профиля меняется только после проверки конфигурации,
  запуска и health-check. При сбое выполняется автоматический rollback.
- Официальный профиль всегда присутствует и является default/fallback.

## Размещение в интерфейсе

В шапке экрана каждого движка появляется компактная строка:

```text
Xray   v26.3.27   UwuRay   [Источник] [Обновить]
Mihomo v1.19.32   mihomo-enhanced   [Источник] [Обновить]
```

Строка отражает фактическое установленное состояние. Если профиль только выбран,
но ещё не установлен, это явно показывается отдельным статусом, например
«Выбран, не установлен».

Кнопка «Источник» открывает модальное окно конкретного движка. Кнопка «Обновить»
доступна только если для сохранённого профиля получен актуальный release metadata
и найден подходящий asset для архитектуры устройства.

Основная рабочая поверхность модуля (редактор Xray или Mihomo) не превращается в
мастер установки: управление компактно доступно в шапке и раскрывается только по
действию пользователя.

## Модальное окно

Верхняя часть окна показывает факт, а не намерение:

```text
Xray
Установлено: v26.3.27
Источник: UwuRay
Состояние: работает
Архитектура: mipsle-softfloat
```

Ниже находится список allowlisted профилей. Для каждого профиля отображаются:

- название и владелец/репозиторий;
- краткое описание отличий;
- последний stable-релиз и дата публикации;
- наличие asset для архитектуры роутера;
- наличие checksum;
- уровень риска или пометка «экспериментальный»;
- ссылка на репозиторий.

Профиль без asset для текущей архитектуры остаётся видимым, но недоступным для
выбора с объяснением причины. Это лучше полного скрытия: пользователь видит,
почему нужный форк нельзя поставить на данном роутере.

Кнопки окна:

```text
[Отмена] [Вернуть официальный] [Сохранить выбор]
```

После сохранения меняется только источник. Интерфейс не должен создавать
впечатление, что бинарник уже заменён.

## Профили первой версии

Каталоги движков содержат стабильные `profile_id`, а не принимаемые от клиента
URL. Начальный allowlist:

### Xray

- официальный `XTLS/Xray-core`;
- `MakostaDev/UwuRay`;
- `GFW-knocker/Xray-core`.

### Mihomo

- официальный `MetaCubeX/mihomo`;
- `LOVECHEN/mihomo-enhanced`;
- `legiz-ru/Prizrak-Core`.

Allowlist является curated-признаком доверия проекта, а не утверждением, что
форк безопасен сам по себе. UI должен показывать репозиторий и предупреждать об
альтернативном/экспериментальном источнике. Фактическая целостность скачанного
asset подтверждается checksum из release metadata.

Профиль описывается декларативно:

```text
profile_id
engine_id
repo
display_name
description
risk_level
release_policy = stable_only
asset_resolver
checksum_policy
binary_name
```

`asset_resolver` учитывает архитектуру, endianness, ABI и формат конкретного
репозитория. Нельзя предполагать единое имя asset: например, Prizrak-Core
публикует `prizrak-core-*`, но устанавливаемый бинарник должен стать `mihomo`.

## Состояния и метаданные

Для каждого движка сохраняются независимо:

```text
selected_profile_id      выбранный источник
selected_profile_status  выбран, но не установлен / установлен / ошибка
installed_profile_id     источник реально установленного бинарника
installed_version        фактическая версия бинарника
release_metadata         последний полученный stable metadata
backup_metadata          данные для автоматического отката
```

Ключевой инвариант: `selected_profile_id` никогда не считается установленным
только потому, что пользователь нажал «Сохранить выбор».

UI обрабатывает состояния:

- загрузка каталога и release metadata;
- свежие данные;
- GitHub недоступен, доступен последний кэшированный результат;
- подходящий asset отсутствует;
- checksum отсутствует или не проходит проверку;
- профиль выбран, но не установлен;
- профиль установлен и активен;
- установка завершилась rollback.

## Поток установки

«Обновить» открывает подтверждение с конкретными данными:

```text
Будет установлен: Alpha-<build>
Для роутера: mihomo-linux-mipsle-softfloat-<build>.gz
Проверка: SHA-256 из checksums.txt
Текущий бинарник будет сохранён для автоматического отката.

[Отмена] [Установить]
```

Установка выполняется общей инфраструктурой как одна заблокированная операция:

```text
подготовка stable-релиза
→ выбор asset под архитектуру
→ скачивание во временный файл
→ проверка checksum
→ backup текущего бинарника и метаданных
→ атомарная замена
→ проверка версии и конфигурации
→ перезапуск сервиса
→ health-check
→ commit или автоматический rollback
```

Панель показывает только фактически выполненные этапы: подготовка релиза,
проверка архива, backup, установка, preflight, перезапуск и health-check.

Если любой шаг после backup не проходит, восстанавливаются прежний бинарник и
прежние метаданные. Пользователь получает причину, а фактический
`installed_profile_id` остаётся прежним. Одновременная установка и ручное
переключение ядра блокируются.

## Ownership и API

`engine.xray` и `engine.mihomo` владеют своими UI, allowlist и resolver-ами.
Общая инфраструктура владеет только транзакцией скачивания, проверкой, backup,
заменой, rollback и health-check.

Предпочтительные module-owned endpoints:

```text
GET  /api/xray/core-profiles
POST /api/xray/core-source
POST /api/xray/core-install/prepare
POST /api/xray/core-install/apply
GET  /api/xray/core-install/status

GET  /api/mihomo/core-profiles
POST /api/mihomo/core-source
POST /api/mihomo/core-install/prepare
POST /api/mihomo/core-install/apply
GET  /api/mihomo/core-install/status
```

Endpoint передаёт общей инфраструктуре `engine_id` и стабильный `profile_id`.
Клиент не передаёт произвольный URL, asset name или команду shell.

## Ошибки и безопасность

- Нельзя устанавливать релиз без checksum.
- Нельзя скачивать asset в путь бинарника напрямую; используется временный файл
  и атомарная замена.
- Пути backup и временные файлы проверяются на принадлежность доверенному каталогу.
- Установка требует блокировки, чтобы исключить гонку с переключением ядра или
  второй установкой.
- Ошибки сети, HTTP, checksum, распаковки, preflight и health-check должны иметь
  разные машинные коды и понятное русское описание.
- Кэш release metadata помечается stale, если GitHub недоступен; stale-данные не
  должны автоматически запускать установку без повторного подтверждения.
- Проверенный профиль означает попадание в версионируемый allowlist проекта;
  произвольный репозиторий не должен попасть в этот поток через параметры API.

## Совместимость с «Командами»

Старые `-ux` и `-um` остаются рабочими и отображаются как низкоуровневые команды.
Status-плашки обновления в «Командах» могут временно показывать текущую версию и
ссылку на релиз, но не должны конкурировать с новым выбором профиля. После
миграции основного flow их можно заменить на ссылку «Открыть управление ядром»
в соответствующем модуле.

## Тестирование и приёмка

### Unit

- каталог профилей валиден и не содержит дубликатов `profile_id`;
- resolver правильно выбирает asset Xray/Mihomo для поддерживаемых архитектур;
- отсутствие asset/checksum блокирует установку;
- имена нестандартных бинарников нормализуются в ожидаемые `xray`/`mihomo`;
- stale-кэш не становится основанием для бесшумной установки.

### Backend/API

- Xray endpoint не возвращает Mihomo-профили и наоборот;
- выбор профиля сохраняется без изменения бинарника;
- подготовка требует текущий stable metadata и подходящий checksum;
- параллельная установка отклоняется;
- ошибки каждого этапа приводят к rollback и корректным метаданным.

### E2E

- открытие источника из Xray и Mihomo показывает разные каталоги;
- сохранение профиля меняет только selected state;
- подтверждение показывает точный tag, asset и checksum policy;
- успешная установка обновляет установленный источник только после health-check;
- сбой показывает rollback и прежнюю версию;
- GitHub offline показывает кэш с пометкой stale;
- старые `-ux/-um` из «Команд» продолжают открываться.

### Приёмка

1. Пользователь выбирает проверенный профиль в модуле двигателя, не заходя в
   «Команды».
2. Выбор не меняет бинарник до отдельного подтверждения установки.
3. Без checksum кнопка установки недоступна.
4. После неуспешного preflight/старта прежнее ядро автоматически возвращается.
5. В UI различаются выбранный профиль и реально установленный профиль.
6. Официальный источник можно восстановить тем же модальным окном.
7. Разделение `engine.xray`/`engine.mihomo` не требует дублирования
   транзакционного установщика.

## Будущий advanced-режим

Произвольный репозиторий добавляется отдельным явно опасным потоком, например в
DevTools или расширенных настройках. Он должен иметь собственное подтверждение,
явный ввод владельца/репозитория и tag, обязательную проверку checksum,
предупреждение о неподтверждённом источнике и отдельный журнал. Он не должен
расширять allowlist или менять базовый каталог проверенных профилей.
