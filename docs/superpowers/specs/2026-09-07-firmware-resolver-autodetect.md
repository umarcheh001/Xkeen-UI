# Автоопределение резолвера прошивки для локальных зон DNS-over-VLESS

Дата: 7 сентября 2026. Проверено на роутере Keenetic-6005 (`192.168.10.1`, KeeneticOS 5.1.4).

## Задача

В карточке DNS-over-VLESS есть поле «Локальные DNS для домашних имён». Пока в него ничего
не вписано, правило `xk_dns_over_vless_local` не создаётся, и **все** домашние имена
уезжают резолвиться на другую сторону тоннеля. Вписать туда нужно адрес резолвера
прошивки — но пользователь не может его знать: это `127.0.0.1` с нестандартным портом,
который панель сегодня упоминает только текстом в сообщении об ошибке
(`services/dns_over_vless.py`, `_parse_local_resolver`, код `local_resolver_loop`).

## Что измерено на роутере

**Резолвер прошивки без политики недоступен.** У KeeneticOS четыре процесса `ndnproxy`:

```
pid 29177  -c /var/ndnproxymain.conf      <- главный, без dns_*_port, т.е. слушает 53
pid 29178  -c /var/ndnproxy_Policy0.conf  dns_udp_port = 41100  (XKeen)
pid 29179  -c /var/ndnproxy_Policy1.conf  dns_udp_port = 41101  (XKeen-ALL)
pid 29180  -c /var/ndnproxy_Policy2.conf  dns_udp_port = 41102  (Незарегистрированные)
```

Порт 53 забрал Xray — это делает сама наша функция. У главного `ndnproxy` в netstat
не осталось ни одного слушающего DNS-сокета, только `127.0.0.1:54321` (rpc). Значит
принимать запросы могут лишь резолверы политик.

**Политика клиента на выбор не влияет.** К локальному резолверу обращается Xray от
своего имени, с роутера; метка соединения клиента в этой цепочке не участвует. И это
не потеря: для домашних имён три резолвера политик неразличимы.

- `static_a`-подмены у Policy0/1/2 совпадают побайтово (общий md5 `38f32a40dd33e6a6866168893e9a021c`);
- имена LAN все берут из общего `/var/ndnproxyhostmap.conf` (файл передан всем четырём процессам);
- запрос `mydigusoffice.netcraze.pro` к 41100, 41101 и 41102 даёт один и тот же ответ `198.51.100.11`.

Отличаются конфиги политик ровно двумя вещами: своим `dns_*_port` и номерами локальных
обёрток DoT/DoH (`40516-40526` против `40532-40542` — те же семь апстримов). Разница
между политиками касается только пути **наружу**, а наружу через этот резолвер мы не
ходим: `skipFallback: true` и список одних лишь локальных зон.

**Зачем это вообще нужно.** У роутера имя KeenDNS `mydigusoffice.netcraze.pro`. Резолвер
прошивки отдаёт на него `198.51.100.11` — маркер TEST-NET-3, под который в nat заведено
23 правила, включая `-A PREROUTING -d 198.51.100.11/32 --dport 443 -j _NDM_HTTP_DNAT_EA_NDNS_`.
Тот же запрос через Xray возвращает публичные адреса облака (`87.228.71.67`,
`95.213.212.50`), и клиент идёт к собственному роутеру через интернет. На момент
измерения через Xray резолвили минимум четыре хоста плюс десять устройств, заведённых
в цепочку `XKEEN_UI_DNS`.

## Настоящий риск — нумерация портов

Порт назначается по порядку, а имени политики не соответствует: на втором роутере
(`192.168.45.1`, та же 5.1.4) политики называются `Policy0`, `Policy1`, `Policy3`, а порты
у них 41100, 41101, 41102 — то есть у `Policy3` порт вовсе не 41103. Вычислять адрес по
номеру политики нельзя, только читать из конфигурации. Политику удалили или пересоздали —
записанный адрес указывает в никуда. Панель об этом не узнаёт:
политики живут в прошивке, а фрагмент Xray статичен.

Деградация тихая: резолвер молчит, глобальный `disableFallback` у нас выключен, зона
уходит на публичный апстрим через тоннель. Домашние имена ломаются без единой ошибки
в интерфейсе.

## Решение

1. **Находить порты самим.** Читать `/var/ndnproxy_*.conf`, брать `dns_udp_port`,
   отдавать список `127.0.0.1:<порт>`. Это быстрое чтение файлов, без `ndmc` — в отличие
   от `services/dns_clients.py`, который умеет назвать резолвер устройства
   (`firmware_resolver`), но опрашивает прошивку и потому вынесен в отдельный
   медленный эндпоинт `/api/routing/dns-over-vless/clients`. Вдобавок правила
   `_NDM_HOTSPOT_DNSREDIR`, из которых `dns_clients` достаёт порт, заводятся только для
   политик, где есть хотя бы один хост, — конфиги же есть у всех.

2. **Подставлять при включении.** Если пользователь ничего не вписал и в состоянии
   ничего не сохранено — использовать найденное. Явно очищенное поле остаётся пустым:
   это осознанный выбор.

3. **Записывать все найденные порты сразу.** Зоны едут копией на каждый резолвер
   (`_local_server` вызывается на каждый адрес), лимит `MAX_LOCAL_RESOLVERS = 16` это
   позволяет. Исчез один порт — отвечают остальные.

4. **Пересверять в сторожевом цикле.** У защиты `dns-over-vless` в `services/dns_guard.py`
   уже есть `reconcile` (`_watch_xray_dns`), который на здоровом такте чинит то, что
   прошивка успела переделать. Туда же добавляется сверка адресов: набор разошёлся —
   переписать и перезапустить ядро, но не чаще раза в час.

5. **Показывать в карточке.** Под полем — строка с найденными адресами и кнопка
   «подставить»; если записанный адрес среди найденных отсутствует — предупреждение.

## Границы

- Разделение локального разрешения имён по политикам клиента **не делается** и в этой
  схеме невозможно: измерения выше показывают, что оно и не нужно.
- Главный `ndnproxy` (`ndnproxymain.conf`) в список не попадает: у него нет `dns_*_port`,
  то есть он на 53, а 53 — это сам Xray, и такой адрес уже отвергает
  `_parse_local_resolver` как петлю.
- Список зон не трогаем — он обновлён отдельно (`KEENETIC_ZONES`, `NETCRAZE_ZONES`).

## Критерии приёмки

1. `GET /api/routing/dns-over-vless` возвращает `firmware_resolvers` — список адресов,
   найденных в конфигурации прошивки (пустой там, где прошивки нет).
2. Включение функции без явного адреса записывает найденные адреса в состояние и
   создаёт правило `xk_dns_over_vless_local`.
3. Явно очищенное поле оставляет функцию без локального резолвера.
4. Здоровый такт сторожа при разошедшемся наборе адресов переписывает конфигурацию,
   и не чаще раза в час.
5. В карточке видно, что нашла панель, и видно расхождение с записанным.
