# Отделение фронтенда Mihomo по образцу Xray

Дата: 2026-11-13. Статус: подход согласован владельцем, подготовлен план реализации.
База исследования: pre-release, e3ed9536.
Независимая проверка реализуемости: существенных пробелов не выявлено.

## Зачем и что согласовано

Владелец попросил отделить Mihomo «как делали с Xray» и подтвердил,
что речь об отделении фронтенда и стилей от core. engine.mihomo уже существует
в реестре (1.0.6), но отсутствует в SEPARATE_MODULES отдельной сборки Vite.
Файлы исходников могут принадлежать модулю в архиве, оставаясь связанными
с общей сборкой: одной классификации файлов недостаточно.

Результат — самостоятельная сборка клиентской части engine.mihomo с существующим
контрактом доступа к core. Изменения внутреннего JS/CSS Mihomo не меняют файлы
core и других модулей. Изменение реализации core не пересобирает Mihomo,
если публичный контракт сохранён. Интерфейс и поведение сохраняются.

## Подходы

1. Повторить существующий Xray: отдельная Vite-сборка, лёгкий вход модуля,
   ленивые части, общий module_parts и импорты xk-core. Это выбранный владельцем
   подход; используем действующие упаковщик, import map и установщик.
2. Ввести новый версионированный host API вместо xk-core. Это потребовало бы
   отдельной миграции оболочки и Xray, не нужно для этой задачи.
3. Только перегруппировать файлы архива. Дешевле, но не устраняет связность
   сборки и поэтому не достигает цели.

## Границы и ограничения

- В модуле: редактор/панель Mihomo, Clash UI (включая журнал), импорт узлов,
  proxy tools, HWID-подписки, DNS/YAML-инструменты, функциональность генератора,
  их compat-адаптеры, собственные ресурсы и специфичные стили.
- В core: навигация и жизненный цикл верхних экранов, общая оболочка редактора,
  авторизация/HTTP, общий runtime, модальные окна, общие UI-компоненты, флаги,
  общие стили журналов и дизайн-токены. Имя файла с mihomo само по себе не
  доказывает принадлежность модулю: panel.mihomo_header.js используется общей
  оболочкой; загрузочные заглушки тоже принадлежат core.
- Backend, протоколы API, форматы конфигурации и пользовательские данные не
  перерабатываются. При необходимости исправляется только упаковка зависимостей.
- Новых зависимостей и нового загрузочного фреймворка не добавляем.
- Не копируем stateful-функции core в модуль. В исходном режиме xk-core должен
  разрешаться к тем же исходным ES-модулям, которыми пользуется оболочка.
- Публикация, теги, установка на роутер и изменение версии вне необходимых
  требований упаковщика не являются частью этого согласования.

## Архитектура

### Входы и ленивые части

Добавить engine.mihomo в vite.module.config.mjs. Отдельный лёгкий
mihomo.module.entry.js предоставляет load(part) и activate(context), по образцу
xray.module.entry.js. Существующий module_parts получает запись engine.mihomo;
его кеш и singleton остаются в core.

Текущую реализацию panel.mihomo.bundle.js перенести внутрь сборки модуля.
Прежний путь оставить загрузочной заглушкой core, аналогично Xray.
Панель продолжает использовать существующий panel.module_loader.

Все вызовы из core в приватные части Mihomo переводятся на модульный вход:
panel.lazy_bindings.runtime.js, загрузка генератора и найденные при проверке
графа остальные потребители. Сохраняются порядок compat-инициализации,
повтор отложенного клика, обработка ошибок и возможность повторной загрузки.
Генератор открывается напрямую и через SPA; его функциональный bootstrap
принадлежит модулю, общая регистрация экрана и shell остаются в core.
Трекер актуальности асинхронной активации сохраняется.

### Общие зависимости

Относительные импорты через границу module/core заменяются публичными
xk-core/<path>. Внутренние относительные импорты Mihomo сохраняются.
Используется действующий сбор публичных core-входов в vite.config.mjs.
Существующие публичные пути не переименовываются. Необходимые новые пути
фиксируются тестом контракта; экспортировать весь core заранее нельзя.

Проверяются не только статические импорты, но и import(), compat-цепочки,
исходный режим, import map и установочная транзитивная зависимость xk-core.
Отдельная проверка предотвращает две копии runtime/module_parts и двойную
регистрацию обработчиков при переходах между экранами.

### Стили

Специфичные для Mihomo правила из общих CSS переносятся в принадлежащие модулю
ресурсы. Смешанные блоки делятся по реальным потребителям. Общие xk-xlog,
модальные примитивы, шапка и флаги остаются в core. Порядок каскада, media queries,
тёмная/светлая темы и существующие размеры должны сохраниться.

Адрес собственного CSS определяется внутри модуля (например, new URL относительно
его JS), чтобы хеш CSS не попадал в core-заглушку. Ресурс должен работать и
в Vite-сборке, и при загрузке исходников без Vite. Встроенный ?inline/?url без
поддержки исходного режима не подходит.

Для загрузки переиспользовать логику ensureModuleStyle из panel.module_loader:
при необходимости вынести её небольшой общий механизм с параметрами ключ/URL
в core. Сохранить один promise на ресурс, ожидание load, удаление неуспешного
link и очистку кеша для повторной попытки. Импорт модуля сам по себе не должен
выполнять DOM-операции: стили подготавливаются перед активацией его UI/части.
Генератор и модальные инструменты получают стили независимо от посещения панели.
Ошибка CSS обрабатывается существующим путём ошибки активации, без тихого успеха.

### Сборка, владение и установка

Сборка выпускает engine.mihomo в frontend-build/modules/engine.mihomo с собственным
манифестом. Основная сборка не включает приватные реализации Mihomo.
Классификация исходников и собранных файлов задаётся явно там, где эвристика имени
ошибается (прежде всего core-заглушки). JS, CSS и ресурсы модуля входят в его пакет,
а общие ресурсы не дублируются. Описи перегенерируются штатной командой.

Установщик и модульные профили используют действующие механизмы. Если проверки
покажут незамкнутую зависимость, исправляется существующий механизм, а не создаётся
параллельная упаковка. При отсутствующем engine.mihomo оболочка/Xray остаются
работоспособны, Mihomo не импортируется заранее; доступность его экранов следует
существующему реестру и состоянию модулей.

## Проверки и критерии приёмки

Новые проверки сначала должны выявлять нынешнюю связанность, затем проходить
после отделения. Существующие проверки границ расширяются для engine.mihomo.

1. Статический и собранный граф: нет обходных импортов приватных частей через
   границу, module/core имеют верное владение, import map и публичные пути полны.
2. Два контрольных пересбора в изолированной копии: изменение внутреннего JS
   Mihomo и отдельно его CSS меняет ноль файлов вне engine.mihomo; изменение
   реализации общего core-помощника меняет ноль файлов внутри engine.mihomo.
   Сравниваются содержимое и имена распространяемых файлов; исключения допустимы
   только для явно служебных общих отчётов/индексов сборки, не runtime-ресурсов.
   Контрольные изменения не остаются в рабочем коде.
3. Исходный и собранный режимы: открытие панели Mihomo, журнал, импорт, proxy tools,
   HWID, DNS/YAML, генератор напрямую и через SPA, возврат и повторный вход.
   Нет двойной инициализации, потери несохранённого текста и запоздалой активации
   уже закрытого экрана. Проверяется повтор после ошибки загрузки JS/CSS.
4. Скриншоты настоящей панели в двух темах: журнал (свёрнутый/раскрытый), редактор,
   модальное окно и генератор; сравнение с исходным видом. Это проверка сохранения
   вида, нового дизайна и макетов не требуется.
5. Профиль без Mihomo: панель и Xray загружаются, нет запросов приватных файлов
   удалённого модуля и ошибок отсутствующих импортов. Упакованный пакет Mihomo
   замкнут по зависимостям; проверяется установка/обновление в тестовой файловой
   системе без доступа к роутеру.
6. Профильные JS/Python/e2e тесты, затем обязательные общие проверки сборки,
   границ, упаковки и полный Python. Полный e2e gate обязателен перед будущим
   выпуском по правилам проекта; пройденные проверки и ограничения фиксируются.

## Порядок доставки и совместимость

Сначала отделение интегрируется в новую базовую сборку панели: она добавляет
загрузочную границу и необходимые публичные core-пути. После её публикации
возможен самостоятельный выпуск engine.mihomo для этой базы по RELEASING.md.
Текущий beta.28 не объявляется совместимым с новым самостоятельным пакетом
без отдельной проверки/адаптации; такая обратная совместимость сюда не включена.

Результат задачи — код отделения, тесты, измерение независимости и проверенный
локальный архив/пакет для просмотра. Пуш/релиз и установка выполняются только
по соответствующей просьбе владельца.

## Решения исполнителя

Использовать существующий Xray-контракт без нового host API; оставить общие
флаги/стили журналов в core; ожидать собственный CSS при активации; проверить
независимость побайтовым сравнением сборок. Это технические решения в рамках
подтверждённого владельцем подхода.

Точные имена частей load(part), группировка собственных CSS и порядок небольших
коммитов определяются планом по реальному графу зависимостей. Они не меняют
границы задачи. Любое необходимое изменение пользовательского поведения либо
расширение публичного контракта за пределы фактических зависимостей возвращается
на обсуждение.
