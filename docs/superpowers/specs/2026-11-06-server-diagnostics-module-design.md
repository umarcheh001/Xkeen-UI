# Модуль «Диагностика серверов» (`tool.server-diagnostics`)

Дата: 06.11.2026. Автор спецификации: Claude по решениям владельца (olmer2002).

## Зачем

Окно «Диагностика серверов» (коллега, `82fcc038`, `286054b2`, `7f1cbbe7`, `2b94da14`) сейчас встроено в core:
маршруты `/api/provider-diagnostics/*` регистрируются при любом движке, окно вставлено в каждую страницу панели,
кнопки «Серверы» стоят на экранах Xray и Mihomo. Часть проверок отправляет адреса серверов из конфигураций
пользователя во внешние сервисы: `dns.google` (сравнение DNS) и `cheburcheck.ru` (реестр блокировок),
а проверка через ядро ходит на `cp.cloudflare.com`.

Владелец не хочет, чтобы это стояло у всех. Решение: вынести функцию целиком в отдельный модуль, который
**не ставится по умолчанию**. Дальше модуль дорабатывает коллега как хочет — своими выпусками модуля, не трогая core.

## Цели

- Без установленного модуля панель не отправляет адреса серверов никуда: нет маршрутов `/api/provider-diagnostics/*`,
  нет окна, нет кнопок «Серверы», нет подсказок «Проверить серверы» в сообщениях об ошибках.
- Модуль не входит в наборы готовых профилей (Full, Legacy-full, xray-minimal, mihomo-minimal). Ставится только
  явно: ответом «да» на отдельный вопрос после выбора Full, выбором в Custom-меню или кнопкой в «Модулях».
- С установленным модулем всё работает как сейчас: те же кнопки, окно, подсказки, проверки.
- Файлы модуля принадлежат модулю по карте принадлежности сборки, так что правка коллеги внутри модуля
  требует подъёма только версии модуля и может выходить отдельным выпуском модуля (этап 1 независимых выпусков).

## Не цели

- Не меняем логику проверок, тексты окна, вид окна. Код переносится как есть (кроме точек подключения).
- Не добавляем выключатель внешних запросов внутри модуля — это дело коллеги.
- Не делаем ревью логики проверок.
- Не выносим функции движков, которые зовёт модуль, в публичный договор движков (см. п. 7а).

## Чего избежать

- Панель без модуля падает, показывает пустую кнопку, ломает экраны Xray/Mihomo или e2e.
- Модуль тихо ставится обновлением: у пользователей с профилем Full он не должен появиться после обновления панели.
- Модуль частично остаётся в core (например, маршруты), и запросы наружу возможны без модуля.

## Ограничения

- Список модулей пока зашит в core (`MODULE_DEFINITIONS`, `BLUEPRINT_OWNERS`, `MODULE_IDS`, шаблоны) — этап 2
  спецификации `2026-11-01-independent-module-releases-design.md` не сделан. Значит, модуль впервые приезжает
  с выпуском панели (ближайшая бета), а дальше обновляется отдельно.
- Принадлежность файлов модулям считается по именам в `module_profile_install.py` (`_module_for_path` и соседние
  правила) и `_PACKAGE_OWNER_OVERRIDES` в `scripts/build_modular_panel_release.py`. Новые правила должны отдать
  модулю ровно его файлы и не задеть чужие (`provider` встречается в Mihomo: `mihomo_rule_provider_inspector.py`,
  `rule-provider` в шаблонах).
- У тех, кто сейчас на beta.21–22, окно было в core. После обновления панели оно пропадёт, пока модуль не поставят.
  Владелец это допускает (бета).
- Описи (`docs/modular-panel-stage0-inventory.*`, `module-sizes.json`) — только `npm run inventory:refresh`;
  контракты `docs/modular-panel-stage4.1-contract.*`, `stage4.6-compatibility.json` и др. — их генераторами.

## Подходы

1. **Отдельный модуль `tool.server-diagnostics`** — выбран владельцем. Всё уходит в модуль, по умолчанию не ставится.
   Цена — регистрация модуля в ~15 местах, как при выносе Xray и диагностики.
2. Вложить в `tool.advanced-diagnostics`. Подключение уже есть, работы меньше, но этот модуль входит в Full и стоит
   почти у всех — адреса уходили бы наружу по-прежнему. Отклонено.
3. Оставить в core и выключить внешние запросы настройкой. Меньше всего работы, но модуля нет и коллега продолжает
   править core. Отклонено.

## Устройство

1. **Определение модуля.** В `services/module_registry.py` новая запись `ModuleDefinition`:
   - `id="tool.server-diagnostics"`, `name="Диагностика серверов"`;
   - `description` прямо говорит о внешних запросах и о нужном движке, например: «Проверка доступности серверов
     из конфигураций Xray и Mihomo. Нужен модуль Xray или Mihomo. Часть проверок отправляет адреса серверов во
     внешние сервисы (dns.google, cheburcheck.ru).» (решение владельца: в карточке видно, что без Xray или Mihomo
     от модуля нет толку). Если ни Xray, ни Mihomo не активны, плитка модуля в «Модулях» показывает это
     предупреждением рядом с кнопкой установки (по образцу существующих предупреждений плиток; установку не
     запрещать — движок могут поставить следом). То же — в пункте Custom-меню установщика: «нужен Xray или Mihomo».;
   - `dependencies=("core",)`. Модуль полезен только при Xray или Mihomo: зависимость «любой из движков» реестр
     сейчас не выражает. Решение Claude: ставить зависимость только от core, а кнопки и маршруты показывать при
     активном модуле **и** соответствующем движке (как сейчас — маршруты регистрировались при любом движке);
   - `removable=True`, `can_disable=True`, `requires_restart=True`, `system_requirements=()`;
   - `frontend_bundles` / `navigation_views` — по образцу `tool.advanced-diagnostics`.
   `BLUEPRINT_OWNERS["provider_diagnostics"] = "tool.server-diagnostics"`, метка установки в
   `_MODULE_INSTALL_MARKERS` — маршрут и сервис модуля.
2. **Файлы модуля** (не переименовываются — так коллеге проще сливать; новые файлы модуля — стили, слоты — могут
   называться `server_diagnostics*`, правило принадлежности покрывает оба имени):
   - `routes/provider_diagnostics.py`, `services/provider_diagnostics.py`;
   - `static/js/features/provider_diagnostics.js`;
   - `templates/panel/modals/provider_diagnostics.html`;
   - тесты `tests/test_provider_diagnostics.py`, e2e `e2e/provider_diagnostics.spec.mjs` (тесты в пакет не входят,
     но остаются про модуль).
3. **Сервер.** `routes/__init__.py` регистрирует блюпринт только при `module_active("tool.server-diagnostics")`
   и активном Xray или Mihomo. В `routes/pages.py` окно подключается записью композиции с владельцем
   `("tool.server-diagnostics",)` вместо `("core",)`. В `pageConfig` новый флаг (например `hasServerDiagnostics`)
   по образцу `has_diagnostics`.
4. **Кнопки «Серверы»** на экранах `routing.html` (Xray) и `mihomo.html` выводятся только при активном модуле
   (через слоты модуля, п. 6а). Без модуля — нет кнопки, а не скрытая/неработающая.
5. **Фронтенд.**
   - `panel.screen.bootstrap.js` больше не импортирует `provider_diagnostics.js` статически. Окно грузится через
     вход модуля `xk-module/tool.server-diagnostics` (importmap, `vite.module.config.mjs`, `SOURCE_FALLBACKS`
     в `services/frontend_importmap.py`, при необходимости запись в `panel.module_loader.js`) — так же, как
     `tool.advanced-diagnostics`. Без модуля нет записи importmap и ничего не грузится.
   - Подсказка `provider_diagnostics_hint.js` остаётся в core (её импортируют модули Xray — по публичному имени
     `xk-core/js/features/provider_diagnostics_hint.js` — и Mihomo; список публичных имён core в
     `tests/test_module_boundaries.py`). Она перестаёт что-либо добавлять, если модуль не активен (флаг `pageConfig`).
     Так модули движков не зависят от нового модуля и их версии не меняются из-за него. Подсказка — короткий
     файл без сетевых запросов, поэтому в core допустима.
6. **Стили (решение владельца: у модуля).** ~216 правил `xk-provider-check*` переезжают из `panel-operator.css`
   в собственный файл модуля (например `static/server-diagnostics.css`), который подключается только при активном
   модуле. Файл принадлежит модулю по карте принадлежности. Снимки e2e на стенде с модулем не должны измениться
   (порядок каскада: файл модуля подключается после `panel-operator.css`). Если какое-то правило окна нужно и без
   модуля (общая рамка окон и т. п.) — оно остаётся в core; правила `xk-provider-check-error-hint` для подсказки —
   по месту подсказки (см. п. 5).
6а. **Кнопки «Серверы» — у модуля.** Кнопки на экранах Xray и Mihomo выводятся через слоты-вставки в шаблонах
   экранов (как `core_source_control_partials`), а сами вставки — шаблоны модуля (например
   `templates/panel/slots/server_diagnostics_xray.html` / `_mihomo.html`, запись композиции с владельцем
   `("tool.server-diagnostics",)`; при необходимости и движком). Так правка кнопок поднимает версию модуля, а не
   движков. Шаблоны экранов меняются один раз — добавляется слот. Правило принадлежности слотов — модулю, до правил
   по `/mihomo` и `/xray` в `templates/panel/`.
7. **Установка.**
   - `scripts/module_profile_install.py`: `tool.server-diagnostics` в `MODULE_IDS`, но **не** в `PRESETS["full"]`
     и `PRESETS["legacy-full"]` (они сейчас равны `MODULE_IDS` — развести явно). Метка установки в `INSTALL_MARKERS`.
     То же в `PROFILE_PRESETS` реестра (`services/module_registry.py`): там `"full"`/`"legacy-full"` тоже равны
     `MODULE_IDS`, и без разведения выбор Full через API поставит модуль. Тест сверяет оба набора.
     Правило принадлежности файлов модулю по именам `provider_diagnostics` (и, при переименовании, `server_diagnostics`)
     в `routes/`, `services/`, `static/js/`, `templates/panel/` — **до** общих правил по `mihomo`/`xray`.
     Исключение: `static/js/features/provider_diagnostics_hint.js` → core.
   - Синхронно `_PACKAGE_OWNER_OVERRIDES` в `build_modular_panel_release.py` при необходимости.
   - `services/module_transactions/install_state.py`: модуль в списке известных.
   - `scripts/install_custom_menu.py`: пункт «Диагностика серверов — проверка серверов, обращается к внешним сервисам»,
     по умолчанию не отмечен.
   - **Full с отдельным вопросом (решение владельца).** Сразу после выбора Full установщик спрашивает:
     «Поставить „Диагностику серверов“? Проверки отправляют адреса серверов во внешние сервисы (dns.google,
     cheburcheck.ru). [y/n]». Ответ только явный — y/n, да/нет, д/н; Enter переспрашивает (как вопросы про дополнения,
     `project_installer_optional_prompts`). Вопрос задаётся только при новой установке Full; при обновлении
     существующей — нет.
   - **«Дополнения» профиля.** Вводится понятие необязательного модуля профиля (пока один — `tool.server-diagnostics`).
     Набор «Full ∪ любые дополнения» по-прежнему называется Full (`module_set_name`, `_physical_profile` и сводка
     «Модулей»), в том числе когда модуль поставлен позже кнопкой в «Модулях». Обновление панели с профилем Full
     (`--keep-switches`, профиль пересчитывается по `PRESETS`) **сохраняет** уже установленные дополнения и **не
     добавляет** неустановленные. Без этого обновление молча снесёт модуль у тех, кто его поставил.
   - Существующая установка с профилем Full при обновлении модуль не получает. Существующая Custom-установка —
     тоже нет (список модулей сохранён).
   - **Обновление со старой панели (решение владельца, вариант 1).** Обновление кнопкой в панели рассчитывает
     набор модулей кодом уже стоящей панели, а там «full» = все модули нового выпуска
     (`services/module_profile_plan.py::_selected_for_release`). Значит, первое обновление со старой версии (3.0.x,
     beta ≤ 22) на выпуск с модулем поставит его молча, и исправить это новым кодом нельзя. Поэтому новая панель
     ведёт **метку явного выбора** модуля: она пишется, когда модуль выбран явно — «да» в установщике, Custom со
     списком, установка или включение кнопкой в «Модулях». При запуске панели: модуль установлен и включён, а метки
     нет — модуль **выключается** (не удаляется; выключенный не регистрирует маршруты и ничего не отправляет) и в
     журнал панели пишется одна строка. В «Модулях» он виден выключенным, включается одной кнопкой (включение ставит
     метку). Новый же `_selected_for_release` при «full» исключает необязательные модули, которых нет среди
     установленных.
   - **Без терминала** (`XKEEN_UI_INSTALL_PROFILE` задан, нет tty): Full без модуля, вопроса нет. Поставить модуль
     без терминала — профилем custom с перечнем в `XKEEN_UI_INSTALL_MODULES`.
7б. **Явный выбор профиля (решение владельца, отдельный коммит).** В меню профиля `install.sh` Enter больше не выбирает
   Full: подсказка «Выбор [1-4]:», пустой ответ переспрашивает. Запуск без tty и с `XKEEN_UI_INSTALL_PROFILE` — как сейчас
   (Full по умолчанию, но без дополнений). Тесты `tests/test_install_terminal_ui.py` и соседние — под новое поведение.
7а. **Зависимость от кода движков.** `services/provider_diagnostics.py` во время работы импортирует
   `xray_outbounds`, `xray_observatory`, внутренние функции `xray_subscriptions` (`_probe_outbounds_batch`,
   `_find_xray_binary`, `_start_probe_process`), `mihomo_proxy_parsers`, `mihomo_runtime._mihomo_binary`; разбор
   vless-ссылки зовёт `build_proxy_outbound_from_link` и при `core == "mihomo"`. Решение Claude: логику проверок не
   менять, но (1) импорты кода движков обернуть так, чтобы без установленного движка проверка отвечала понятным
   отказом (400 с текстом «нужен модуль Xray/Mihomo»), а не 500 от `ImportError`; (2) сторожевой тест перечисляет
   все имена движков, которые импортирует модуль, — переименование внутри движка роняет тест, а не модуль у
   пользователя. Вынести эти функции в публичный договор движков — дело коллеги позже.
8. **Интерфейс «Модулей».** Значок плитки в `module_manager/render.js` (например `ping` — тот же, что у окна).
9. **Версии.** `module-versions.json`: `"tool.server-diagnostics": "1.0.0"`. Шаблоны экранов Xray и Mihomo
   меняются (добавляется слот) — версии `engine.xray`/`engine.mihomo` поднять; `check_module_versions_for_release.py`
   подскажет, если затронуто что-то ещё.
10. **Стенды и тесты.**
    - `scripts/run_e2e_server.py` включает модуль, чтобы текущий `provider_diagnostics.spec.mjs` и снимки работали.
    - Новый e2e или pytest «панель без модуля»: нет кнопок «Серверы» на экранах Xray/Mihomo, нет окна в разметке,
      `/api/provider-diagnostics/targets` отвечает 404, подсказка «Проверить серверы» не появляется при сетевой ошибке.
    - pytest: Full/Legacy-full (и `PRESETS` установщика, и `PROFILE_PRESETS` реестра) не содержат модуль; Custom
      с модулем содержит; «Full + модуль» называется Full; обновление Full сохраняет поставленный модуль и не
      добавляет непоставленный; вопрос установщика про модуль (y/n, Enter переспрашивает, без tty — нет); меню
      профиля без Enter; модуль без движка отвечает 400, а не 500; сторож имён движков, которые импортирует модуль; карта принадлежности относит файлы модуля
      модулю, а подсказку — core; `rule-provider`/`mihomo_rule_provider_inspector.py` остаются у Mihomo.
    - Тест окон (`test_modular_panel_stage4_4_modals.py`, `stage4_5_composition.py`) и контракты — под нового владельца.
    - Полный `npm run test:py`, `npm run frontend:build`, затем `npm run e2e:gate`.

## Порядок работ (крупно)

1. Тесты «без модуля», «профили», «вопрос установщика» — падают.
2. Реестр, владельцы, профили, установщик, состояние установки.
3. Сервер: условная регистрация, композиция страницы, флаг `pageConfig`, условные кнопки.
4. Фронтенд: вход модуля, загрузчик, подсказка по флагу.
5. Версии, описи, контракты, e2e-стенд.
6. Отдельным коммитом — явный выбор профиля в установщике (п. 7б).
7. Полный прогон, затем e2e:gate. Коммиты локально; пуш и бета — по слову владельца.

## Риски

- Коллега продолжает править эти файлы — конфликты. Коллега предупреждён и согласен (06.11.2026); файлы не
  переименовываются.
- Правило по слову `provider` заденет файлы Mihomo — проверяется тестом принадлежности.
- Снимки экранов Xray/Mihomo в e2e: на стенде модуль включён, снимки не меняются; без модуля снимков нет.

## Что оставлено исполнителю

- Имя флага в `pageConfig` и способ условия в шаблонах.
- Где именно регистрировать вход модуля в загрузчике.
- Значок плитки.

## Решения Claude, которые стоит проверить владельцу

- Зависимость только от core; кнопки и маршруты — при модуле и нужном движке.
- Подсказка «Проверить серверы» остаётся в core и молчит без модуля.
- Обёртка импортов движков с отказом 400 и сторожевой тест имён (п. 7а).
- Описание модуля прямо называет внешние сервисы.
