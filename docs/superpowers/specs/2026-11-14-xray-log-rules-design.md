# Правило маршрутизации в журнале Xray

Дата: 14.11.2026. База исследования: b3e2a1a8.
Статус: реализовано и проверено 14.11.2026; изменения в pre-release без коммита.

## Задача

Помочь отладке маршрутизации: показать ruleTag реально сработавшего правила
рядом с маршрутом соединения, по аналогии с журналом Mihomo. Приоритет владельца:
сохранить ускорение пакетной отрисовки Xray. Не вычислять предполагаемое правило
повторным исполнением конфигурации и не угадывать по outbound.

## Согласованное поведение

- Колонка «Правило» доступна только в access, если есть непустой ruleTag в
  JSON-фрагментах роутинга, предназначенных для запуска ядра, и текущий уровень
  ядра — info/debug.
  JSONC-черновики/отключённые правила не являются источником наличия тегов.
- Видимость не зависит от переключателя показа доменов.
- При отсутствии подтверждённого сопоставления — «—», без вывода об отсутствии
  правила или о маршруте по умолчанию.
- Не проставлять ruleTag автоматически, не менять уровень логов автоматически
  ради этой колонки, не перезапускать ядро ради её отображения.

## Подходы

1. **Выбранный в обсуждении:** сопоставление диагностического журнала с access,
   переиспользование существующего фонового чтения и пакетной отрисовки.
   Работает со штатным ядром, но требует осторожного поведения при потерях.
2. Повторный поиск правила в конфигурации по назначению: не выбран, поскольку
   не воспроизводит достоверно DNS/sniffing/порядок и прочий контекст ядра.
3. Отдельный API-поток: в RoutingContext API Xray 26.11.9 нет ruleTag;
   отдельный поток не решает задачу и расширяет изменение.

## Предложение вида

Настоящий экран Xray с дополнительной колонкой между «Маршрут / узел» и
«Порт». В ячейке — точный ruleTag без перевода и новых цветов маршрутов.
Длинный тег обрезается многоточием, полное значение доступно в подробностях.
Без колонки размеры и размещение прежние. На узком экране правило остаётся
в подробностях, если для колонки недостаточно места.

Раскрытие: отдельное поле «Правило» с точным тегом, для неизвестного —
«Не определено». Сырые access/error сохраняются дословно. В TSV правило
передаётся отдельной колонкой при включённом показе, исходная строка остаётся
последней колонкой. Копирование оригиналов не меняется. Новые фильтры и
сводка по правилам в первую версию не входят.

## Источники и надёжность

Диагностические сообщения Hit route rule содержат ruleTag и session ID.
У AccessMessage session ID отсутствует. Для dokodemo-door на info есть
received request for с исходным endpoint. Сессию сопоставлять с учётом
источника и порта, протокола, исходного/распознанного назначения, outbound и
времени. При повторном использовании endpoint или нескольких кандидатах не
брать последний тег произвольно. Отсутствие обязательных данных — «—».

Sniffing routeOnly проверен локально: access-IP и routing-домен отличаются.
Использовать сведения одной сессии, включая явный target из tunneling request to;
не использовать общий кеш доменов по IP как доказательство правила.
Проверенные сначала inbound — dokodemo-door TCP/UDP; прочие форматы поддерживать
только при наличии полного и проверенного набора ключей, иначе «—».

Индекс сессий/сопоставлений ограничен размером и временем жизни. Не хранить его
в localStorage. При смене поколения логов (рестарт, очистка, ротация, пропуск
хвоста) сбрасывать незавершённые связи. Уже присвоенные записи не переназначать
по более новым сессиям. На паузе не менять отображаемый снимок и его метаданные.

Присвоенный тег хранить у конкретной записи, а не получать из изменяемого
endpoint-кеша при раскрытии или TSV. После возобновления применять отложенные
метаданные, пока соответствующие записи ещё находятся в буфере.

Не финализировать связь посреди диагностического хвоста. Для первой реализации
предлагается ограниченное окно сопоставления до 2 секунд и подтверждение, что
диагностический курсор догнал конец файла за этим окном; при тихом журнале
учитывать время успешного чтения конца файла. Это инженерный выбор, подлежащий
проверке на реальном корпусе, а не гарантия ядра. До подтверждения — «—».
Если окно не даёт однозначного результата, данные потеряны или уже вытеснены,
не расширять поиск бесконечно. Позднее противоречие может только снять
подтверждение (вернуть «—»), но не подменить один тег другим.

Наличие тегов определять по применённым конфигурационным фрагментам существующими
средствами сервера; не читать большие routing JSON на каждое событие access.
Достаточно передавать признак наличия тегов вместе с существующим статусом,
с кешированием по составу/mtime фрагментов. При ошибке чтения не считать,
что информация о наличии тегов достоверна. Контракт видимости — конфигурация
на диске, которую загружает служба, а не недоступный снимок памяти процесса.
Это инженерное уточнение: после ручного изменения файла без рестарта колонка
может изменить доступность раньше ядра. Сам ruleTag всегда берётся из сообщения
ядра, а не из нового содержимого файла. Не вводить отдельную систему снимков
конфигурации ядра ради определения доступности колонки.

## Сохранение скорости

- Существующий приём access, инкрементальные счётчики, виртуализация и один
  DOM-проход за requestAnimationFrame остаются основой.
- Один существующий diagnostic-опрос обслуживает домены и правила. При отсутствии
  потребителей чтение не добавлять. Обработка правил не зависит от показа доменов.
- Каждую новую diagnostic-строку разбирать один раз; никаких поисков по всему
  журналу/конфигурации для каждой access-записи. Получение тега — из индекса.
- Начальную большую пачку разбивать с ограничением времени работы и уступкой
  главному потоку. Обновления данных объединять; не пересоздавать DOM таблицы
  или всю её оболочку при появлении каждого тега.
- При отставании diagnostic-курсора ограничивать чтение свежим окном. Явно
  сообщать клиенту о пропуске/смене поколения и инвалидировать незавершённые
  связи. Не догонять без ограничения всю историю и не учащать опрос бесконтрольно.
- Пауза/смена файла/уровня/уход со вкладки отменяют или отделяют устаревшую
  фоновую работу. Показ колонки меняется только при изменении её доступности.

Ответ diagnostic-чтения должен позволять отличить обычный append от reset/
пропуска и сообщать, достигнут ли конец файла. Известные перезапуски/очистки
сбрасывают связи независимо от inode; inode и offset сами по себе не защищают
от усечения с быстрым повторным ростом. Курсор связывать с поколением и
небольшой проверкой прочитанной границы, без повторного чтения всего файла.
Начальная очередь и её обработка тоже ограничены: переполнение инвалидирует
незавершённые связи. В view обновлять метаданные по seq; новый тег не должен
менять общий decoVersion всех строк. Опрос без потребителей определяется
показом доменов ИЛИ доступностью правил и существующим жизненным циклом вкладки.

Исследование: prototype Chromium CPU×4, 128 КиБ — медиана 2.4 мс,
1 МиБ — 81.1 мс. Текущий опрос 128 КиБ/2.5с может отставать на сильном потоке.
Подробности: .superpowers/xray-rules-investigation.md.

## Проверки и приёмка

Сначала падающие проверки, затем реализация. Покрыть:
- наличие тегов в разных применённых фрагментах, отключённые/JSONC-правила,
  отсутствие тегов и ошибки чтения; info/debug против warning/error/none;
- парсер и сопоставление TCP/UDP, IPv6, одинаковый outbound у разных правил,
  перемешанные сессии, sniffing, повторный endpoint, потери/неполные данные;
- разбиение пачек, лимиты индекса/очереди, пропуск хвоста, ротацию/рестарт,
  паузу, уход/возврат и поздние ответы;
- UI-видимость независимо от доменов, длинный/опасный HTML-тег как текст,
  раскрытие, TSV/raw, узкий экран, сохранность пакетирования access/error.

Сборка перед e2e. Связанные JS/Python/e2e и прежние регрессии пакетирования.
Повтор A/B на неизменённой базе и реализации: 5/50/500 событий/с, CPU×1/×4,
буфер500, высота360px, не меньше3 повторов; diagnostic-поток заполнен и включает
начальный хвост/отставание. Сравнивать одинаковые входные данные, обработку
очереди, p95 задержки DOM, long tasks, память и отсутствие потери access.
При воспроизводимом замедлении выяснить причину и исправить до заявления
о готовности; одиночный шумный замер не доказывает ни регрессию, ни её отсутствие.

Проверка на роутере/установка, коммит, пуш, теги и выпуск не входят в разрешение
на реализацию. Для установки требуется отдельная команда владельца.

## Уточнения при реализации и ревью

Продуктовый код реализован после принятия макета. Принимать transport dialing
как исходное назначение нельзя: это адрес upstream. Поддержан явный target
из tunneling request to VLESS/VMess/Trojan/Shadowsocks; для direct routeOnly
без такого свидетельства — «—». Проверено локальным VLESS-стендом.
Отозванная запись получает постоянный ruleRevoked; два скалярных временных
cutoff при eviction/TTL не позволяют объявить оставшегося кандидата уникальным.
Независимое ревью подтвердило закрытие всех трёх Important.
Проверка скорости выявила лишнюю работу на приёме access. Убрано inline
сопоставление: обновления тегов выполняются только после фоновой пачки.
Доменные кандидаты не нормализуются, если у строки нет ни session ID, ни
IP-назначения, которое могло бы обогатить кеш. Корреляция sniffed-only строк
с session ID сохранена. Инвариант отсутствия inline lookup проверен e2e.
