# Управление LTE-модемами в диагностике роутера

Раздел `Диагностика роутера → LTE / модемы` показывает состояние модемов,
которое Keenetic отдаёт через RCI, и даёт безопасную проверку транспорта
управления для конкретной карточки. Управление привязано к RCI-идентификатору
модема: соседний USB-модем не может быть выбран только по порядку устройств.

## Кнопки и источники данных

- `Обновить` повторно читает LTE inventory через RCI и обновляет карточки,
  сигнал, сеть, адрес, IMEI и остальные поля штатной диагностики.
- `Проверить управление` выполняет read-only probe. Он не меняет режим модема,
  не отправляет reset и не создаёт отдельный сервис.
- `Перезапустить модем` становится доступной только после успешного probe,
  когда backend доказал соответствие транспорта конкретному RCI-модему.
  Перед отправкой команды открывается подтверждение с именем и точным RCI id.

Проба и reset используют backend панели с фиксированными аргументами
подпроцесса. Пользовательский ввод не превращается в shell-команду, путь к
устройству или имя процесса.

## Как выбирается транспорт

Backend повторно получает RCI inventory и находит только указанный `modem_id`.
Проверка не принимает модель, имя или путь устройства из браузера как источник
истины.

1. Сначала перебираются character devices `/dev/cdc-wdm*`. Для каждого
   выполняется короткий read-only запрос `qmicli --dms-get-ids`.
2. QMI считается принадлежащим карточке только при совпадении IMEI с IMEI из
   RCI. При совпадении QMI получает приоритет.
3. Если QMI не подтверждён, проверяются `/dev/ttyUSB*`. Для кандидата
   выполняются `AT` и `AT+CGSN` на безопасной скорости 115200; TTY принимается
   только при ответе `OK` и совпадении IMEI с RCI.

Порядок `/dev/ttyUSB*` и фиксированный `/dev/ttyUSB1` не являются способом
выбора модема. Если RCI не содержит IMEI, IMEI не совпал или устройство не
открывается, probe возвращает безопасное состояние без транспорта. Отсутствие
`qmicli` отключает только QMI-проверку: при совпавшем по IMEI TTY probe всё ещё
может вернуть доступный AT fallback. Сырые ответы QMI/TTY и IMEI не включаются
в состояние операции.

Обычный probe и предварительная проверка перед reset имеют общий лимит 12
секунд для всех QMI/TTY-кандидатов. Поэтому неответившие или устаревшие device
files возвращают безопасную причину из backend до тайм-аута запроса в браузере.
Для QMI-проверки на роутере должен быть заранее установлен `qmi-utils`
(`qmicli`); панель не устанавливает этот пакет сама.

## Reset и восстановление

Reset доступен только для существующего RCI id и требует JSON-подтверждения:

```json
{"confirmation":"UsbQmi1"}
```

При подтверждённом QMI отправляется `qmicli -d <проверенный-путь>
--dms-set-operating-mode=reset`. TTY используется только как fallback после
проверки IMEI и получает `AT+RESET`. Backend сохраняет безопасный snapshot до
операции, ждёт исчезновения и возврата именно этого RCI id, затем возвращает
итоговый snapshot. Потеря сети во время перезапуска ожидаема; успехом считается
подтверждённый возврат модема, а не наличие интернет-маршрута в ту же секунду.

Статусы операции:

| Статус | Смысл |
| --- | --- |
| `queued` | Команда принята и поставлена в очередь фонового worker. |
| `running` | Команда reset выполняется. |
| `waiting_for_modem` | Backend ждёт возврата модема в RCI. |
| `recovered` | Тот же RCI id снова найден; итоговый snapshot получен. |
| `failed` | Команда или проверка транспорта завершилась ошибкой. |
| `timed_out` | Команда была отправлена, но возврат не подтверждён за лимит. |

Для одного модема допускается одна активная операция. История хранится только
в ограниченном in-memory реестре процесса и удаляется после TTL. API операции:

- `POST /api/system/router/lte/<modem_id>/probe` — read-only capability probe;
- `POST /api/system/router/lte/<modem_id>/reset` — reset после подтверждения,
  ответ `202` с `operation_id`;
- `GET /api/system/router/lte/operations/<operation_id>` — текущий статус.

Типовые безопасные причины отказа: `modem_not_found`,
`transport_not_matched`, `qmi_tool_missing`, `qmi_probe_timeout`,
`modem_confirmation_mismatch`, `modem_operation_in_progress` и
`modem_recovery_timeout`. Эти ответы не содержат stderr, командных строк,
IMEI или путей устройств.

## Первый аппаратный прогон

До первого reset обновите модалку и выполните `Проверить управление` только на
карточке `T2_STATIC` (`UsbQmi1`). Сверьте, что в статусе указан именно
`T2_STATIC` и выбранный transport (`QMI` либо `AT`). Если transport не найден,
остановитесь на диагностике и соберите причину из UI/API; ручной fallback по
порядку `/dev/ttyUSB*` запрещён.

После read-only проверки можно выполнить reset `T2_STATIC`:

1. Нажать `Перезапустить модем` на карточке `T2_STATIC`.
2. В подтверждении проверить имя `T2_STATIC` и RCI id `UsbQmi1`.
3. Дождаться `Восстановлен` либо явно зафиксировать `failed`/
   `timed_out` и сохранить статус операции.
4. Нажать `Обновить` и сравнить срез до reset: сеть, адрес, сигнал, базовую
   станцию и доступность интерфейса.

Первый аппаратный прогон авторизован только для `T2_STATIC`. Модем `Beeline`
не перезапускать и не использовать для проверки reset. Не изменять APN, band,
PIN или режим сети в рамках этой процедуры.

## Что не устанавливается

Код управления встроен в существующий authenticated backend панели. Он не
устанавливает автоматически `qmi-utils`, `libqmi` или `uhttpd_kn`, не меняет
права на устройства и не создаёт CGI. Отдельный HTTP-сервис на `:8080` не
устанавливается и не запускается. Скрипты `setup_modem_reset.sh` и
`setup_modem_reset2.sh` используются только как reference низкоуровневых
команд.

Если требуется вернуть обычное состояние диагностики после теста, достаточно
дождаться терминального статуса операции и нажать `Обновить`. Повторный reset
до завершения текущей операции backend отклонит.
