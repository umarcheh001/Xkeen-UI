# Применение подписок Xray и восстановление после ошибки

Относится к [issue #43](https://github.com/umarcheh001/Xkeen-UI/issues/43).

## Горячее применение REALITY

При `XKEEN_SUBSCRIPTIONS_HOT_APPLY=1` ручное и плановое обновление могут
применить ротацию `serverName` / `shortId` через HandlerService, сохранив PID
Xray и существующие соединения. По умолчанию настройка выключена. Она доступна
в DevTools → ENV и не требует перезапуска панели.

В окне «Подписки Xray» есть общий переключатель «Обновление без перезапуска»
и справка рядом. При включении панель сама настраивает локальный HandlerService,
проверяет дерево и запускает API одним перезапуском Xray. Уже готовый API
используется без перезапуска. Остальные API-сервисы и комментарии сохраняются;
внешний адрес API автоматически не меняется. При ошибке возвращаются прежние
файлы и настройка. Выключение переключателя не удаляет API, которым могут
пользоваться другие функции. Переключатель не меняет расписание подписок.
Старая схема API через routing требует ручного перехода на `api.listen`:
автоматическая замена отключила бы доступ существующим API-клиентам.

API необходимо явно настроить в конфигурации Xray, например:

```json
{
  "api": {
    "tag": "api",
    "listen": "127.0.0.1:10085",
    "services": ["HandlerService", "RoutingService"]
  }
}
```

После добавления API один раз примените конфигурацию обычным перезапуском.
При ручной настройке используется числовой loopback-адрес; удалённый или общий
интерфейс запрещён для горячего применения. Автонастройка выбирает свободный
локальный порт, сохраняя его в конфигурации.

Условия: новое дерево проходит `xray -test`; набор файлов и тегов outbound
совпадает; меняются только REALITY SNI/shortId у VLESS без Mux. Маршруты,
selectors, Observatory, leastPing, fallback и DNS остаются прежними.
Прежде чем менять runtime, панель компилирует оба набора outbound тем же
бинарником Xray и проверяет полное совпадение прежних outbound с API.
После применения проверяется полное совпадение с новым набором.

HandlerService не предоставляет атомарную замену: выполняются RemoveOutbound
и AddOutbound с прежним тегом. Уже открытые потоки сохраняют старый handler;
новое соединение в короткий промежуток замены может попасть на резервный узел
или потребовать повтора. Абсолютная непрерывность всех новых подключений не
гарантируется. Изменение адреса, ключей, состава узлов, маршрутов или Mux
применяется обычным перезапуском. Параметры аутентификации не игнорируются.

При ошибке API возвращаются старые handlers и проверяется откат. Затем панель
применяет проверенную конфигурацию через restart. Если откат runtime нельзя
подтвердить и restart тоже отказал, требуется восстановительный запуск старого
дерева даже при ещё работающем процессе. Отсутствующие команды API, несовпавший
runtime или неподдерживаемая сборка до первой мутации используют обычный restart.
Используется CLI самого ядра, без зависимости от `grpcio` и без привязки к форку.

## Восстановление

При неудачном restart возвращаются прежние конфиги, JSONC и состояние подписок.
Если ядро остановлено, восстановленная конфигурация должна пройти отдельную
проверку самим Xray перед восстановительным запуском. Ошибка записи при откате
или невозможность проверить дерево запрещает запуск.

Восстановление старой конфигурации не считается успешным обновлением:
`ok=false`, `restarted=false`, `recovered=true`. Неудачный восстановительный
запуск возвращает `recovery_failed`. Ошибка остаётся в состоянии подписки;
следующая попытка использует существующий интервал повторения ошибок.
Запуск подтверждается одним и тем же PID, наблюдаемым не менее секунды.

## Проверки 14 ноября 2026

Один набор из 12 интеграционных сценариев запускается на настоящих ядрах:

- официальный Xray `26.3.27`, Windows amd64;
- официальный Xray `26.11.9`, Linux amd64;
- установленный на роутере Jolymmiles `26.10.13-2347`, Linux arm64,
  Python 3.13.9, панель `3.0.3-beta.28+local.955a15d0`.

Проверяются автонастройка API, выключение и повторное включение без restart,
отказ некорректного outbound, сохранение RoutingService,
обычный restart и его отказы, побайтный откат файлов и восстановление ядра.
Сетевые сценарии поднимают локальный REALITY-сервер и TLS-decoy, TCP echo,
HTTP-пробу Observatory и DNS. Сначала используется резервный VLESS, затем
leastPing выбирает наблюдаемый узел по selector-префиксу. При ручном и пакетном
обновлении SNI/shortId оба открытых TCP-потока продолжают передавать данные,
PID сохраняется, новые подключения и DNS по VLESS работают. Искусственный
отказ AddOutbound проверяет реальный откат и переход к restart.

На роутере кандидат запускается во временном каталоге отдельно от установленной
панели и рабочего Xray. Дополнительно в приватной копии действующих конфигов и
состояния дважды обновлены обе подписки устройства: 20 и 2 узла. Все загрузки
и проверки дерева успешны. Рабочие конфиги и состояние не изменены; PID
рабочего Xray до и после прогона — `6282`. Обновление установленной панели
не входит в этот прогон.

```sh
XKEEN_REAL_XRAY=/opt/sbin/xray PYTHONPATH=xkeen-ui \
  python3 -m pytest tests/test_xray_handler_service_local.py -q
```

Без `XKEEN_REAL_XRAY` интеграционные проверки пропускаются. Регрессии отказов
покрыты `test_xray_handler_service.py`, `test_xray_subscriptions.py`,
`test_xray_subscriptions_rollback.py` и `test_xkeen_service_control_fallback.py`.
